# Принципы архитектуры

По ним проверяется каждый PR.

## Переиспользование — одна реализация на весь проект

| Что | Где | Кто пользуется |
| --- | --- | --- |
| Ошибки `problem+json`, middleware, graceful shutdown | `backend/internal/platform/httpx` | api, admin-api |
| Жизненный цикл HTTP-бинарника | `backend/internal/platform/server` | api, admin-api |
| Конфиг, логи, пул БД, миграции, очередь | `backend/internal/platform/{config,logx,db,migrate,queue}` | все бинарники |
| Тестовая база, проверка по контракту | `backend/internal/platform/testkit` | тесты всех модулей |
| Контракт API | `contracts/openapi` | Go-сервер, TS-клиенты, позже Dart |
| Токены дизайна | `contracts/tokens/tokens.json` → `@wf/tokens` | веб, админка, позже Flutter |
| Локализация: fallback и сверка ключей | `@wf/i18n` | веб, админка |
| Конфиги TS, ESLint, Prettier | `@wf/config` | все JS-пакеты |

Общий код выносится при втором реальном потребителе или когда это граница платформы.
Абстракции «на всякий случай» не делаем.

Новый модуль бэкенда, которому нужны свои SQL-запросы, — это новый элемент списка `sql`
в `backend/sqlc.yaml` со своими `queries/` и `out`, и обязательно с `omit_unused_structs: true`:
в пакет модуля попадают только модели его собственных запросов, а не вся схема целиком
(без этого флага один запрос тянет за собой файл на тысячи строк).

## Масштабирование без костылей

- API без состояния в памяти процесса: сессии и идемпотентность — в базе. Второй инстанс
  за балансировщиком не требует изменений кода.
- Модули общаются через интерфейсы верхнего уровня и события outbox; в чужие таблицы не ходят.
  Вынос модуля в сервис — замена реализации интерфейса.
- Worker масштабируется отдельно: очередь River в Postgres, задачи не задваиваются.
- Пул, таймауты, число воркеров — из конфига, не из кода.

## Границы, которые проверяются автоматически

- `cmd/api` и `cmd/worker` не зависят от админского кода — ни одного пакета `wf/backend/...`
  с сегментом пути `admin` (`internal/httpapi/admin`, `internal/<модуль>/admin`) и `cmd/admin-api`:
  `backend/internal/archtest` (транзитивно, главный страж); depguard ловит прямые импорты
  `internal/httpapi/admin` и `cmd/admin-api` (сравнивает пакеты только по префиксу).
- Изоляция модулей (спека бэкенда §3–4, §12) — `backend/internal/archtest`:
  - `modules.go` — слои модулей (`Layers`) и пары `intx` (`IntxPairs`): модуль импортирует
    только корневой пакет нижнего модуля и `intx` из списка; платформа не зависит от
    модулей, `internal/httpapi` и `archtest`; немодульные пакеты (`httpapi`, `platform`,
    `archtest`) видят у модуля только корневой пакет, `httpapi` и `admin`; модуль берёт из
    `internal/httpapi` только сгенерированные типы `oapi` в своих `httpapi/` и `admin/`;
    каталог `internal/<имя>` вне `Layers` — ошибка;
  - `ownership.go` — владелец каждой таблицы, представления и функции схемы (`Schema`):
    SQL модуля (`internal/<модуль>/queries`) пишет только свои таблицы, чужое читает только
    из экспортированных представлений `<модуль>_read_*`; объект схемы без владельца или
    устаревшая запись карты — ошибка; каталог `queries` в `backend/sqlc.yaml` вне
    `internal/<модуль>/queries/` и `internal/platform/<пакет>/queries/` — ошибка (иначе SQL
    выпал бы из проверки). Разбор SQL — `archtest/sqlscan` (`go-pgquery`, без cgo); незнакомая
    форма дерева разбора — ошибка, а не пропуск.
- Контракт: операцию с тегом `<модуль>` реализует хендлер этого модуля (`apitest.TagViolations`,
  тесты `internal/httpapi/{public,admin}`); конвенции бандлов — `contracts/test/conventions.test.mjs`
  (ровно один тег, `operationId` lowerCamel, `x-error-codes`, `Idempotency-Key` у мутирующих операций
  с аутентификацией, анонимные мутации — только из закрытого списка `x-anonymous-mutations`,
  нет внешних `$ref`); у каждого кода ошибки есть текст в локалях веба и админки
  (`src/i18n/error-codes.test.ts`; пустая строка в `ru` — тоже нет текста); коды платформы
  (`httpx.PlatformCodes`) совпадают с `x-error-codes-common` обоих контрактов
  (`TestPlatformCodesDocumented`); ломающее изменение — `./task contracts:breaking` (oasdiff, в CI
  бэкенда; понижения уровней — `contracts/oasdiff-severity.txt`; осознанная ломающая правка
  админского контракта — явной строкой в `contracts/oasdiff-err-ignore-admin.txt`).
- Запрос проверяется по контракту до strict-хендлера (`httpx.ValidateRequests`):
  `400 validation.failed` с `errors: [{field, code}]`.
- `apps/web` и `apps/admin` не импортируют друг друга, пакеты не импортируют приложения —
  eslint-plugin-boundaries (`@wf/config/eslint`): приложения — их `lint`, пакеты — корневой
  `eslint.config.mjs` (`pnpm run lint:packages` в `packages:ci`).
- Клиент админского API существует только в `apps/admin`.
- Сгенерированный код совпадает с контрактами — `backend:gen:check`, тест `@wf/tokens`; бандлы контракта свежие — `contracts/test/bundle.test.mjs`.
- Схема `Problem` одинакова в обоих контрактах — тест в `contracts/`.
- Роли БД (§12.7): `internal/platform/grants/grants_test.go` — под `api` нет доступа к `staff_*` и изменению `audit_log`, под `worker` — к чтению `credentials` (кроме столбца `user_id` для удаления); проверено подсадкой (снятие ветки CASE).
