# Ролевая модель

Кто что может в продукте: роли игроков, роли сотрудников админки, права сотрудников и правило двух
рук. Источник — спека среза «Сотрудники и админка geo»
(`docs/superpowers/specs/2026-10-06-staff-admin-geo2-design.md`, §2) с решениями ревью от 06.10.2026.
Документ проходит отдельное ревью до кода: владелец продукта одобряет модель, затем по ней строится
код.

Таблица прав в разделе 5 **генерируется** из кода (`backend/internal/platform/perm/catalog.go`)
командой `./task gen`. Руками её не править: `./task backend:gen:check` и тест пакета `perm` ловят
расхождение. Всё остальное в документе пишется руками.

## 1. Два мира

| | Игроки (продукт) | Сотрудники (админка) |
| --- | --- | --- |
| Учётка | `users` | `staff_accounts` (рабочая почта) |
| Модуль | `identity`; права на команду — `teams`, на матч — `matches` | `staff` |
| API | `api` (JWT) | `admin-api` (cookie-сессия) |
| Роль БД | `api` | `admin`; у `api` и `worker` доступа к `staff_*` нет |

Один человек может быть и игроком, и сотрудником — это две разные учётки, никак не связанные. Так
обязанности разделены намеренно: взлом публичного API не даёт входа в админку. Всё, что касается
сотрудников (вход, письма, чистка, перешифровка), исполняет `admin-api` под ролью БД `admin`; воркер
продукта ключей и прав на `staff_*` не получает.

## 2. Роли игроков: одно место хранения на роль

| Что | Где хранится | Примечание |
| --- | --- | --- |
| Гость | нет сессии | не роль |
| Игрок | любой активный `users` | не хранится |
| Допуск к капитанству в городе | `role_assignments (captain, city)` | выдаётся одобрением заявки; «испытательный / полный» — свойство допуска |
| Капитан и вице команды | `teams.captain_id`, `teams.vice_captain_id` | права на команду проверяет модуль `teams` |
| Организатор и участник матча | данные матча | права проверяет модуль `matches` |
| Ограничения | `user_restrictions` | запрет, а не роль |
| Платные возможности | права `economy` | не роль |

Модератор и админ — не роли игрока: это сотрудники (раздел 3). После миграции `0020` в
`role_assignments` остаётся только допуск капитана в городе.

## 3. Роли сотрудников: одна роль на человека

| Роль | Код | Скоуп | Назначение |
| --- | --- | --- | --- |
| Владелец | `owner` | глобально | всё, включая выдачу прав; последнего активного владельца снять нельзя |
| Админ | `admin` | глобально | операционное управление: города, флаги, версии, модерация |
| Модератор | `moderator` | список городов | очереди, жалобы, ограничения до 30 дней — в своих городах |
| Поддержка | `support` | глобально | только чтение |

У сотрудника ровно одна роль (`staff_roles`). Список городов (`staff_role_cities`) бывает только у
модератора и не бывает пустым — это держит база (отложенный триггер, миграция `0020`).

## 4. Права

### 4.1. Ключ и значение

- Ключ права — `<модуль>.<ресурс>.<действие>`: `geo.cities.rename`, `staff.roles.grant`.
- Право либо читает (действие `read` или `search`), либо меняет состояние («изменение» в таблице,
  `Mutating` в коде).
- Значение права у роли:

  | В таблице | В коде и API | Смысл |
  | --- | --- | --- |
  | да | `allow` | можно (у права чтения — читать всё) |
  | свои города | `scoped` | можно только в городах модератора |
  | вдвоём | `dual` | операция не исполняется сразу, а создаёт запрос на подтверждение (раздел 7) |
  | нет | `deny` | нельзя |

  Отдельного значения «только чтение» нет: чтение — это отдельное право с действием `read`.

### 4.2. Инварианты матрицы

Их проверяют тесты пакета `perm`; матрица, которая их нарушает, не собирается в зелёный CI.

- Владелец может всё: у `owner` нет `нет` ни в одной строке.
- `свои города` бывает только у модератора — остальные роли глобальные.
- `вдвоём` бывает только у прав изменения.
- Поддержка только читает: все права изменения у неё — `нет`.
- Модератор меняет только в своих городах: права изменения у него — `свои города` или `нет`.
- Выдать роль владельца или админа, снять владельца, снять админа, сбросить доступ владельцу или
  админу — только владелец.
- Удалить запись журнала действий не может никто: такого права нет, а базу защищает триггер
  `audit_log_is_append_only`.

### 4.3. Где проверяется право

Каждая операция контракта admin объявляет расширение `x-permission`. Значение — ключ каталога (не
черновой) или одно из служебных:

| Значение | Кого пропускает | Операции |
| --- | --- | --- |
| `anonymous` | без сессии; у операции `security: []`, мутация идёт без ключа идемпотентности | `staffLogin`, `staffAcceptInvite`, `staffResendInviteSelf` |
| `session` | сессию любой стадии; стадию проверяет сценарий | `staffVerifyMfa`, `staffUnlock`, `staffLogout`, `getStaffMe`, `staffMfaSetup`, `staffMfaConfirm`, `staffRecoveryAck` |
| `self` | активную сессию; только своё | `getStaffMfa`, `regenerateStaffRecoveryCodes`, `changeStaffPassword`, `listStaffMySessions`, `revokeStaffMySession`, `revokeStaffOtherSessions`, `updateStaffMeLocale`, `listApprovals`, `cancelApproval` |
| `handler` + `x-permission-any: [ключи]` | хотя бы одно из перечисленных прав у роли не `нет`; точное право по телу запроса или цели решает сценарий | `createStaffInvite` [`staff.roles.grant`, `staff.roles.grant_elevated`]; `changeStaffRole` [`staff.roles.grant`, `staff.roles.grant_elevated`, `staff.roles.revoke`]; `disableStaffAccount` [`staff.roles.revoke`, `staff.roles.revoke_admin`, `staff.roles.revoke_owner`]; `resetStaffAccess` [`staff.access.reset`, `staff.access.reset_elevated`]; `approveApproval`, `rejectApproval` [все права каталога со значением `вдвоём`]; в плане geo 2/2 — `PATCH /v1/geo/cities/{cityId}` |
| ключ каталога | роль с этим правом не `нет` | `listStaffAccounts`, `getStaffAccount` (`staff.accounts.read`); `resendStaffInvite` (`staff.invites.resend`); `listStaffAccountSessions`, `revokeStaffAccountSessions` (`staff.sessions.revoke`); `getStaffRoles` (`staff.roles.read`); `listAudit` (`audit.log.read`); `listGeoCities` (`geo.cities.read`) |

Конвейер admin-api проверяет значение сам:

- стадия сессии: для `self` и ключей каталога нужна стадия `active` — в стадии `setup` ответ
  `403 auth.setup_required`, в `mfa_pending` — `401 auth.unauthenticated`;
- бездействие больше 20 минут или смена сети: `401 auth.reauth_required` — пока сотрудник не введёт
  второй фактор, доступны только операции `session`;
- нет права — `403 auth.forbidden`, один код на всю админку;
- `свои города` при `cityId` в пути сверяется с городами модератора; без города в пути — сценарий.

Внутри сценария модуль решает через `auth.Staff`: права роли загружаются вместе с сессией
(`perm.Grants`), поэтому модули не импортируют `staff`. `вдвоём` никогда не означает «можно сразу»:
сценарий создаёт запрос на подтверждение.

## 6. Правила назначения

- Владельца и админа назначает только владелец, вдвоём (`staff.roles.grant_elevated`). Модератора и
  поддержку — владелец или админ, вдвоём (`staff.roles.grant`).
- Смена роли или городов (`PUT /v1/staff/accounts/{id}/role`):
  - старая или новая роль — владелец или админ → `staff.roles.grant_elevated`, вдвоём;
  - иначе роль меняется или модератору добавляется хотя бы один город → `staff.roles.grant`, вдвоём;
  - иначе (модератору только убирают города, хотя бы один остаётся) → `staff.roles.revoke`, сразу;
  - пустой список городов у модератора — `400 validation.failed`, несуществующий город —
    `422 staff.city_not_found`.
- Снять роль = выключить учётку (`status = disabled`). Сразу, кроме снятия владельца (вдвоём,
  `staff.roles.revoke_owner`). Админа снимает только владелец (`staff.roles.revoke_admin`), модератора
  и поддержку — владелец или админ (`staff.roles.revoke`). Выключение гасит все сессии сотрудника и
  его ожидающие запросы на подтверждение.
- Последнего активного владельца снять, выключить или лишить доступа нельзя — `409 staff.last_owner`.
  Проверка идёт под одной блокировкой во всех путях, поэтому два владельца не могут одновременно
  выключить друг друга.
- Над собой через управление сотрудниками ничего сделать нельзя — `409 staff.self_action`. Свои
  сессии и пароль — через «Мой доступ».
- Сброс доступа гасит пароль, второй фактор, резервные коды и сессии и выпускает новое приглашение.
  Владельцу и админу — `staff.access.reset_elevated` (владелец, вдвоём), модератору и поддержке —
  `staff.access.reset` (владелец или админ, вдвоём). Самостоятельного «забыл пароль» у сотрудников
  нет: доступ восстанавливает только другой сотрудник — это защита от захвата через почту.
- Повторное приглашение на почту выключенной учётки возвращает ту же учётку через сброс доступа.
  История и журнал сохраняются. Приглашение на почту активной учётки — `409 staff.email_taken`.
- Оператор сервера (доступ к серверу — корень доверия) работает подкомандами `admin-api staff …`:
  `bootstrap` (первый владелец), `invite-resend`, `reset-access` (единственный владелец потерял второй
  фактор), `disable` (снять владельца, когда подтвердить некому). Каждая пишет журнал с ролью
  `operator`. Два владельца на старте — два запуска `bootstrap`: правилу двух рук нужен второй человек.

## 7. Правило двух рук

Действия со значением `вдвоём` один человек не делает — даже владелец: выдача прав, сброс доступа,
снятие владельца, позже вечная блокировка, аннулирование протокола и ручные начисления.

- Операция отвечает `202` и создаёт запрос на подтверждение (таблица `approvals`, механизм платформы
  `platform/approvals`). Исполнителя действия регистрирует модуль; подтверждение исполняет его в одной
  транзакции с данными, журналом и событиями.
- Запрос живёт 24 часа. Статусы: ждёт, исполнен, отклонён, отменён, просрочен, не исполнен
  (`pending`, `executed`, `rejected`, `cancelled`, `expired`, `failed`). Решённые запросы хранятся 180
  дней, затем удаляются (журнал действий о них остаётся).
- Подтвердить или отклонить может сотрудник, у которого то же право со значением `да` или `вдвоём`
  (для `свои города` — город цели в его списке), в активной сессии. Он не инициатор и не цель запроса
  — это держит и база.
- При подтверждении проверяются срок, что инициатор всё ещё активен и имеет право, и версия цели.
  Цель изменилась после запроса — статус «не исполнен», `409 staff.approval_stale`.
- Отменить запрос может только инициатор. Выключение, сброс доступа или смена роли инициатора
  отменяют его ожидающие запросы.
- Входящие видит тот, кто может их подтвердить; счётчик в меню обновляется раз в минуту. Решения по
  действиям `staff.*` на телефоне скрыты («только с компьютера»), это ограничение интерфейса, а не
  защита.
- Каждый шаг пишется в журнал действий.

## 8. Как добавить право

1. Строка в `rows` файла `backend/internal/platform/perm/catalog.go` — коммитом модуля, которому
   право нужно. Пока спеки модуля нет — черновая (`draft(…)`).
2. `./task gen` — таблица этого документа и `contracts/openapi/admin/permissions.json`.
3. Подпись права `permissions.<ключ>` — в `apps/admin/messages/{ru,en}.json` (en — переводом).
4. Операция контракта admin — с `x-permission` (или в `x-permission-any`), ключ не черновой.
5. Тесты `perm` проверяют инварианты раздела 4.2; нарушение — повод пересмотреть строку, а не тест.
