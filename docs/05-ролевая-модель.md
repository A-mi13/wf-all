# Ролевая модель

Кто что может в продукте: роли игроков, роли сотрудников админки, права сотрудников и правило двух
рук. Источник — спека среза «Сотрудники и админка geo»
(`docs/superpowers/specs/2026-10-06-staff-admin-geo2-design.md`, §2) с решениями ревью от 06.10.2026 и
ревью ролевой модели R1 от 07.10.2026. Документ проходит отдельное ревью до кода: владелец продукта
одобряет модель, затем по ней строится код.

Таблица прав в разделе 5 **генерируется** из кода (`backend/internal/platform/perm/catalog.go`)
командой `./task gen`. Руками её не править: `./task backend:gen:check` и тест пакета `perm` ловят
расхождение. Всё остальное в документе пишется руками.

## 1. Два мира

| | Игроки (продукт) | Сотрудники (админка) |
| --- | --- | --- |
| Учётка | `users` | `staff_accounts` (рабочая почта) |
| Модуль | `identity`; права на команду — `teams`, на матч — `matches` | `staff` |
| API | `api` (JWT) | `admin-api` (cookie-сессия) |
| Роль БД | `api` | `admin`; у `api` и `worker` доступа к `staff_*` нет |

Один человек может быть и игроком, и сотрудником — это две разные учётки, никак не связанные. Так
обязанности разделены намеренно: взлом публичного API не даёт входа в админку. Всё, что касается
сотрудников (вход, письма, чистка, перешифровка), исполняет `admin-api` под ролью БД `admin`; воркер
продукта ключей и прав на `staff_*` не получает.

## 2. Роли игроков: одно место хранения на роль

| Что | Где хранится | Примечание |
| --- | --- | --- |
| Гость | нет сессии | не роль |
| Игрок | любой активный `users` | не хранится |
| Допуск к капитанству в городе | `role_assignments (captain, city)` | выдаётся одобрением заявки; «испытательный / полный» — свойство допуска |
| Капитан и вице команды | `teams.captain_id`, `teams.vice_captain_id` | права на команду проверяет модуль `teams` |
| Организатор и участник матча | данные матча | права проверяет модуль `matches` |
| Ограничения | `user_restrictions` | запрет, а не роль |
| Платные возможности | подписка и покупки — модуль `economy` | не роль |

Модератор и админ — не роли игрока: это сотрудники (раздел 3). После миграции `0020` в
`role_assignments` остаётся только допуск капитана в городе.

## 3. Роли сотрудников: одна роль на человека

| Роль | Код | Скоуп | Назначение |
| --- | --- | --- | --- |
| Владелец | `owner` | глобально | всё, включая выдачу прав; последнего активного владельца снять нельзя |
| Админ | `admin` | глобально | операционное управление: города, флаги, версии, модерация |
| Модератор | `moderator` | список городов | очереди, жалобы, ограничения до 30 дней — в своих городах |
| Поддержка | `support` | глобально | только чтение |

У сотрудника ровно одна роль (`staff_roles`). Список городов (`staff_role_cities`) бывает только у
модератора и не бывает пустым — это держит база (отложенный триггер, миграция `0020`).

## 4. Права

### 4.1. Ключ и значение

- Ключ права — `<модуль>.<ресурс>.<действие>`: `geo.cities.rename`, `staff.roles.grant`.
- Право либо читает (действие `read` или `search`), либо меняет состояние («изменение» в таблице,
  `Mutating` в коде).
- Привязка «город» (`CityBound` в коде) — объект права принадлежит городу: город, район, запись
  журнала, заявка, жалоба. Только у таких прав бывает значение `свои города`.
- Значение права у роли:

  | В таблице | В коде и API | Смысл |
  | --- | --- | --- |
  | да | `allow` | можно (у права чтения — читать всё) |
  | свои города | `scoped` | можно только в городах модератора |
  | вдвоём | `dual` | операция не исполняется сразу, а создаёт запрос на подтверждение (раздел 7) |
  | нет | `deny` | нельзя |

  Отдельного значения «только чтение» нет: чтение — это отдельное право с действием `read`.

### 4.2. Инварианты матрицы

Их проверяют тесты пакета `perm`; матрица, которая их нарушает, не собирается в зелёный CI.

- У владельца нет `нет` ни в одной строке; выдача прав и сбросы доступа у него — `вдвоём`.
- Владелец ни в одной строке не строже админа: нет строки, где у админа `да`, а у владельца `вдвоём`.
- Админ не слабее модератора и поддержки ни в одной строке. Сила значения: `да` > `свои города` >
  `вдвоём` > `нет`.
- `свои города` бывает только у модератора — остальные роли глобальные — и только у прав с
  привязкой «город».
- `вдвоём` бывает только у прав изменения.
- Поддержка только читает: все права изменения у неё — `нет`.
- Модератор меняет только в своих городах: права изменения у него — `свои города` или `нет`.
- Выдать роль владельца или админа, снять владельца, снять админа, сбросить доступ владельцу или
  админу — только владелец.
- Права `audit.*` — только чтение: права изменить или удалить запись журнала действий нет ни у кого,
  а базу дополнительно защищает триггер `audit_log_is_append_only`.
- Нечерновые права совпадают со спекой среза (§2.5) в обе стороны: право вне спеки или значение не по
  спеке — красный тест.

### 4.3. Где проверяется право

Каждая операция контракта admin объявляет расширение `x-permission`. Значение — ключ каталога (не
черновой) или одно из служебных. Какая операция какое значение несёт, решает контракт: источник истины —
`x-permission` и `x-permission-any` в `contracts/openapi/admin/`, соответствие проверяет страж
контракта и тест прав ручек admin-api (план A, Task 10b). Здесь — только смысл значений.

| Значение | Кого пропускает | Пример |
| --- | --- | --- |
| `anonymous` | без сессии; у операции `security: []`, мутация идёт без ключа идемпотентности | вход по паролю, принятие приглашения |
| `session` | сессию любой стадии; стадию проверяет сценарий | второй фактор входа, `GET /v1/staff/me` |
| `self` | активную сессию; только своё | «Мой доступ», свои запросы на подтверждение |
| `handler` + `x-permission-any: [ключи]` | хотя бы одно из перечисленных прав у роли не `нет`; точное право по телу запроса или цели решает сценарий | приглашение (`grant` или `grant_elevated` по роли), решение подтверждения |
| ключ каталога | роль с этим правом не `нет` | список сотрудников (`staff.accounts.read`), журнал (`audit.log.read`) |

Конвейер admin-api проверяет значение сам:

- стадия сессии: для `self` и ключей каталога нужна стадия `active` — в стадии `setup` ответ
  `403 auth.setup_required`, в `mfa_pending` — `401 auth.unauthenticated`;
- бездействие больше 20 минут или смена сети: `401 auth.reauth_required` — пока сотрудник не введёт
  второй фактор, доступны только разблокировка (`POST /v1/staff/auth/unlock`), `GET /v1/staff/me` и
  выход (спека §4.7);
- нет права — `403 auth.forbidden`, один код на всю админку;
- `свои города` при `cityId` в пути сверяется с городами модератора. **Без города в пути конвейер
  `свои города` пропускает**: список обязан сам отфильтровать записи по городам модератора, а
  изменение — проверить город цели (`Decide(ключ, cityID)`).

Внутри сценария модуль решает через `auth.Staff`: права роли загружаются вместе с сессией
(`perm.Grants`), поэтому модули не импортируют `staff`. `вдвоём` никогда не означает «можно сразу»:
сценарий создаёт запрос на подтверждение.

### 5.1. Отступления от макета 07

Черновые строки взяты из макета `design/screens/07-Админка.dc.html` («Роли и доступ») с поправками:

- Где макет даёт модератору «да», здесь `свои города` (инварианты раздела 4.2).
- Строка «Разбирать жалобы и споры» (у поддержки «чтение») разделена на право чтения и право решения.
- Журнал модератор читает по своим городам и свои записи, а не «все записи», как в макете.
- **Снятие прав — сразу, без второго (решение U1, 07.10.2026).** В макете строка «Выдавать и снимать
  права» у владельца — «вдвоём». Здесь выдача прав — `вдвоём`, а снятие админа
  (`staff.roles.revoke_admin`, владелец) и модератора или поддержки (`staff.roles.revoke`, владелец или
  админ) — `да`, одним человеком. Отзыв доступа должен быть быстрым (уволенный или взломанный
  сотрудник), а привилегий он никому не даёт. Компенсация: при выключении админа письмо уходит всем
  активным владельцам, кроме инициатора. Снятие владельца остаётся `вдвоём`.

### 5.2. Черновые строки: неполнота и пометки для спек модулей

Список черновых строк **неполный**: в нём только то, что нарисовано в макете 07. Из
`docs/01-домен-и-правила.md` известны ещё действия сотрудников, права на которые заведёт спека
модуля:

- передача капитанства и сброс статистики команды;
- споры о метках оплаты;
- споры и ручная проверка протоколов матчей, очередь аномалий;
- турниры модераторов;
- снятие допуска капитана;
- модерация чата и медиа;
- просмотр карточки игрока без персональных данных.

Пометки к существующим строкам:

- `teams.captains.approve` — заявки на капитанство в модуле `teams`, а допуск
  (`role_assignments`) пишет `identity`: спека определит, через какой интерфейс или событие.
- `moderation.reports.resolve` — споры живут в таблицах `results` и `reputation`, не `moderation`:
  спека определит владельца и интерфейс решения.
- `pitches.pitches.moderate` — публикацию и слияние полей разделить на два права (требование U8 ниже).

### 5.3. Обязательные требования к спекам будущих модулей (решения R1, 07.10.2026)

- **U4, moderation.** Второе ограничение того же игрока в течение 90 дней — только вдвоём или админом.
  Суммарный срок ограничений игрока — не больше 30 дней за 90. Это закрывает цепочку коротких
  ограничений (`moderation.restrictions.apply`) в обход вечной блокировки (`moderation.bans.issue`).
- **U5, moderation и teams.** Необязательная заявленная связь «сотрудник → учётка игрока»: вносит
  владелец, входа она не даёт и служит только запретом действий над собой (своя заявка на капитанство,
  свой спор).
- **U6, identity.** Персональные данные игроков поддержка по всем городам видит только с обязательной
  причиной или номером обращения; каждое чтение — в журнал.
- **U7, economy и geo.** Смена возрастных порогов и валюты страны, где уже открыты города, — `вдвоём`
  (отдельный ключ `geo` в плане B). Награды и задания с начислением кредитов или очков — `вдвоём`:
  это закрывает цепочку `economy.catalog.manage` в обход `economy.credits.grant`.
- **U8, pitches.** Публикация поля — модератор своего города. Слияние полей необратимо — админ или
  модератор с подтверждением вторым. Ключ `pitches.pitches.moderate` разделить в спеке `pitches`.

## 6. Правила назначения

- Владельца и админа назначает только владелец, вдвоём (`staff.roles.grant_elevated`): запрос
  владельца подтверждает только другой владелец — у админа этого права нет. Модератора и поддержку —
  владелец или админ, вдвоём (`staff.roles.grant`).
- Смена роли или городов (`PUT /v1/staff/accounts/{id}/role`):
  - старая или новая роль — владелец или админ → `staff.roles.grant_elevated`, вдвоём;
  - иначе роль меняется или модератору добавляется хотя бы один город → `staff.roles.grant`, вдвоём;
  - иначе (модератору только убирают города, хотя бы один остаётся) → `staff.roles.revoke`, сразу;
  - пустой список городов у модератора — `400 validation.failed`, несуществующий город —
    `422 staff.city_not_found`.
- Снять роль = выключить учётку (`status = disabled`). Сразу, кроме снятия владельца (вдвоём,
  `staff.roles.revoke_owner`). Админа снимает только владелец (`staff.roles.revoke_admin`), модератора
  и поддержку — владелец или админ (`staff.roles.revoke`). Выключение гасит все сессии сотрудника и
  его ожидающие запросы на подтверждение. Выключение админа — письмо всем активным владельцам, кроме
  инициатора (раздел 5.1).
- Последнего активного владельца нельзя снять, выключить, понизить сменой роли или лишить доступа —
  `409 staff.last_owner`. Проверка идёт под одной блокировкой во всех путях, поэтому два владельца не
  могут одновременно выключить друг друга. Исключение — подкоманда оператора `admin-api staff
  reset-access`: она сбрасывает доступ и единственному владельцу (выход из тупика, раздел 6.1).
- Над собой через управление сотрудниками ничего сделать нельзя — `409 staff.self_action`. Свои
  сессии и пароль — через «Мой доступ».
- Сброс доступа гасит пароль, второй фактор, резервные коды и сессии и выпускает новое приглашение.
  Владельцу и админу — `staff.access.reset_elevated` (владелец, вдвоём), модератору и поддержке —
  `staff.access.reset` (владелец или админ, вдвоём). Самостоятельного «забыл пароль» у сотрудников
  нет: доступ восстанавливает только другой сотрудник — это защита от захвата через почту.
- Повторное приглашение на почту выключенной учётки возвращает ту же учётку через сброс доступа с
  новой ролью: право проверяется по новой роли (`staff.roles.grant` или `staff.roles.grant_elevated`),
  старая роль заменяется. История и журнал сохраняются. Приглашение на почту активной учётки —
  `409 staff.email_taken`.

### 6.1. Минимальный состав и выходы из тупиков

Подтверждающий — не инициатор и не цель запроса. Отсюда, сколько владельцев нужно для каждого
действия `вдвоём`:

| Действие | Кто подтверждает | Нужно владельцев | Выход через оператора |
| --- | --- | --- | --- |
| Выдать роль владельца или админа | другой владелец | 2 | `bootstrap` второго владельца |
| Сбросить доступ админу | другой владелец | 2 | `reset-access` |
| Сбросить доступ владельцу | третий владелец (не инициатор и не цель) | 3 | `reset-access` |
| Снять владельца | третий владелец | 3 | `disable` |
| Понизить владельца сменой роли | третий владелец | 3 | нет: только через третьего владельца (`bootstrap`) |
| Выдать роль модератора или поддержки, сбросить им доступ | другой владелец или админ | 1 (и ещё один владелец или админ: всего двое из владельцев и админов) | `bootstrap` второго владельца |
| Снять админа, модератора или поддержку | никто — сразу | 1 | `disable` |

- Один владелец без админов не выдаст ни одной роли: ни владельца, ни админа (подтвердить некому), ни
  модератора с поддержкой (нет второго среди владельцев и админов). Сбросить доступ админу он тоже не
  может.
- Два владельца не могут сбросить доступ, снять или понизить друг друга: цель запроса подтверждать
  не может, третьего нет. Понизить владельца можно только через третьего владельца.
- **Рекомендация: в работе держать трёх владельцев** — тогда тупиков из таблицы нет.
- Оператор сервера (доступ к серверу — корень доверия) работает подкомандами `admin-api staff …`:
  `bootstrap` (новый владелец), `invite-resend`, `reset-access` (сброс доступа, в том числе
  единственному владельцу), `disable` (выключение, когда подтвердить некому). **Подкоманды оператора
  матрицей прав не ограничены**; каждая пишет журнал с ролью `operator`.
- `bootstrap` доступен в любой момент, не только на старте (решение U2, 07.10.2026), и каждый запуск
  отправляет письмо всем активным владельцам: незаметно добавить владельца нельзя. Два владельца на
  старте — два запуска `bootstrap`.

## 7. Правило двух рук

Действия со значением `вдвоём` один человек не делает — даже владелец: выдача прав, сброс доступа,
снятие владельца, позже вечная блокировка, аннулирование протокола и ручные начисления.

- Операция отвечает `202` и создаёт запрос на подтверждение (таблица `approvals`, механизм платформы
  `platform/approvals`). Исполнителя действия регистрирует модуль; подтверждение исполняет его в одной
  транзакции с данными, журналом и событиями.
- Запрос живёт 24 часа. Статусы: ждёт, исполнен, отклонён, отменён, просрочен, не исполнен
  (`pending`, `executed`, `rejected`, `cancelled`, `expired`, `failed`). Решённые запросы хранятся 180
  дней, затем удаляются (журнал действий о них остаётся).
- Подтвердить или отклонить может сотрудник, у которого то же право со значением `да` или `вдвоём`
  (для `свои города` — город цели в его списке), в активной сессии. Он не инициатор и не цель запроса
  — это держит и база; иначе `409 platform.approval_self`.
- При подтверждении проверяются срок и статус (запрос уже решён, отменён или просрочен —
  `409 platform.approval_closed`), что инициатор всё ещё активен и имеет право, и версия цели. Цель
  изменилась после запроса — статус «не исполнен», `409 platform.approval_stale`. Нет запроса —
  `404 platform.approval_not_found`.
- «Не исполнен» ставится и при падении исполнителя: изменения исполнителя откатываются целиком
  (savepoint), статус `failed` и текст ошибки сохраняются.
- Отменить запрос может только инициатор. Выключение, сброс доступа или смена роли инициатора
  отменяют его ожидающие запросы.
- Входящие видит тот, кто может их подтвердить; счётчик в меню обновляется раз в минуту. Решения по
  действиям `staff.*` на телефоне скрыты («только с компьютера»), это ограничение интерфейса, а не
  защита.
- Каждый шаг пишется в журнал действий.

## 8. Как добавить право

1. Строка в `rows` файла `backend/internal/platform/perm/catalog.go` — коммитом модуля, которому
   право нужно. Пока спеки модуля нет — черновая (`draft(…)`). Объект права принадлежит городу —
   обёртка `city(…)`.
2. `./task gen` — таблица этого документа и `contracts/openapi/admin/permissions.json`.
3. Подпись права `permissions.<ключ>` — в `apps/admin/messages/{ru,en}.json` (en — переводом).
4. Операция контракта admin — с `x-permission` (или в `x-permission-any`), ключ не черновой.
5. У права есть `вдвоём` хотя бы у одной роли:
   - исполнитель действия регистрируется в `approvals.Registry.Register` модуля;
   - подпись действия `approvals.actions.<действие>` — в `apps/admin/messages/{ru,en}.json`;
   - операция отвечает `202` со схемой `Approval`;
   - ключ права добавляется в `x-permission-any` у `approveApproval` и `rejectApproval`.
6. У права есть `свои города`:
   - в пути операции — `{cityId}` (конвейер сверит город), иначе сценарий решает через
     `Decide(ключ, cityID)` по городу цели;
   - список обязан фильтровать записи по городам модератора;
   - тест «модератор чужого города» — отказ на изменение и пустой (или без чужих записей) список.
7. Черновая строка становится рабочей вместе со спекой модуля: убрать `draft(…)`, значения — по спеке,
   строка попадает в права ролей и в контракт; пункты 3–6.
8. Тесты `perm` проверяют инварианты раздела 4.2; нарушение инварианта — повод пересмотреть строку, а
   не тест. Права среза тест сверяет со спекой (`spec25` в `catalog_test.go`): значение права среза
   меняется только вместе со спекой §2.5 и `spec25` — одним коммитом.
