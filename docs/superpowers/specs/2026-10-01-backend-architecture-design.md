# Архитектура бэкенда — дизайн

Дата: 2026-10-01. Статус: на ревью.
Этап: архитектура Go-бэкенда целиком — модули и их границы, общие механизмы платформы,
контракт, воркер, admin-api, стражи и порядок реализации. Каждый модуль после этой спеки
получает свой цикл спека → план → код; план этой спеки — «фундамент» (§12, пункт 0).

## 1. Цель и критерий готовности

Бэкенд строится как модульный монолит, который выдерживает весь продукт из `docs/01` и
`product/03` без переделки основы: каждый модуль можно понять, протестировать и вынести
в отдельный сервис заменой реализации интерфейса.

Этап «фундамент» (план этой спеки) готов, когда:

1. все механизмы §5 реализованы в `internal/platform/*` и покрыты тестами;
2. все стражи §11 работают и каждый проверен подсадкой бага;
3. контракт разбит по модулям, бандл собирается, `gen:check` сверяет бандл и Go-код;
4. событие, записанное в outbox тестовым модулем, доходит до двух подписчиков через relay
   и River, повтор доставки не задваивает обработку — сквозной тест на реальной базе;
5. `cmd/api`, `cmd/admin-api`, `cmd/worker` собраны на новой платформе, `./task dev` работает;
6. документация обновлена (§14).

## 2. Принятые решения

| Вопрос | Решение |
| --- | --- |
| Объём | Весь продукт, без урезанного среза и временных обходов доменных правил. Список «Сейчас НЕ делаем» снят: турниры, городские рейтинги, подписки, кредиты, косметика, прогнозы, чат, второй язык строятся полностью и включаются фича-флагами по городам |
| Декомпозиция | Эта спека — архитектура; дальше спека на каждый модуль (§12); UI админки, веб и Flutter — свои спеки |
| Устройство модуля | Модульный монолит, инкапсуляция через `internal/` (проверяет компилятор) + archtest + владение таблицами (§3) |
| Связь модулей | Синхронно — через интерфейс корневого пакета; реакции — через события outbox. Транзакция между модулями — только из явного списка (§4.3) |
| Вход | Почта + пароль, код из письма при регистрации и восстановлении. Соцвходы — позже, таблица `user_identities` сразу. 2FA игроков — позже |
| Капитанство | Подтверждённая почта вместо телефона; телефон — необязательный контакт (§6.1) |
| Антибот | Слои: rate limit, блок-лист одноразовых доменов, ловушки форм, уровни доверия, PoW-капча по протоколу ALTCHA при подозрении; сторонний провайдер — реализация того же интерфейса (§5.7) |
| Устройства | ≤ 2 регистраций на мобильное устройство; входы — мягкий лимит с флагом; связанные аккаунты видны модератору, их голоса и оценки друг другу не засчитываются (§6.3) |
| Веб | Next.js — BFF: токены только на сервере Next, в браузере httpOnly cookie; Go API принимает только Bearer (§7.4) |
| Токены | access — JWT EdDSA 10 мин; refresh — непрозрачный, ротация, детект повтора с окном 30 с (§5.2) |
| Админка | Отдельный бинарник и домен, обязательный TOTP, cookie-сессия `SameSite=Strict` через реверс-прокси (§9) |
| ID | UUIDv7, генерируются в Go |
| Покрытия полей | `pitch_surface` дополняется `rubber`, `sport_floor`; подсказка об обуви — функция (покрытие, тип) (§6.4) |

## 3. Модуль изнутри

```
backend/internal/<модуль>/
  <модуль>.go      публичный API: интерфейс Service, DTO, ошибки, конструктор
  events.go        события, которые модуль публикует, — контракт для подписчиков
  intx.go          интерфейс <Модуль>InTx — только методы из списка §4.3 (если есть)
  internal/
    domain/        чистые правила без БД, HTTP и часов: инварианты, расчёты, переходы состояний
    app/           сценарии: права, транзакция, outbox, вызовы других модулей
    store/         sqlc-пакет <модуль>db + репозиторий поверх него
  httpapi/         хендлеры своей части публичного API (тип oapi ↔ DTO модуля)
  admin/           сценарии и хендлеры admin-api (archtest видит сегмент admin)
  subscribers/     обработчики чужих событий
  jobs/            задачи River модуля
  queries/         SQL модуля
```

- Чужой `internal/` не импортируется — запрещает компилятор Go.
- Другой модуль импортирует только корневой пакет (`wf/backend/internal/teams`): интерфейс,
  DTO, события. Не `httpapi`, не `admin`, не `jobs`.
- `domain/` не импортирует ничего, кроме стандартной библиотеки и `domain/` своего модуля.
  Время передаётся аргументом.
- Публичный API модуля не знает о HTTP: его можно вызвать из воркера или другого транспорта.
- Модуль без правил (справочник) может не иметь `domain/` — пустые слои не создаются.
- Новый модуль — новый элемент `sql` в `backend/sqlc.yaml` с `omit_unused_structs: true`.

## 4. Карта модулей

### 4.1. Владение таблицами

У каждой таблицы ровно один модуль-владелец; читает и пишет её только он. Карта хранится
в коде (`backend/internal/archtest/ownership.go`) и проверяется стражем §11.2.

| Модуль | Таблицы | Отвечает за |
| --- | --- | --- |
| `geo` | countries, regions, cities, districts | справочник, статусы городов, валюта и возрастные пороги страны |
| `identity` | users (ядро аккаунта), credentials, auth_codes, sessions, devices, device_accounts, user_identities, role_assignments, nickname_reservations, nickname_changes, reserved_nicknames, staff_mfa, staff_recovery_codes | регистрация, вход, токены, устройства и связанные аккаунты, роли, ники, удаление аккаунта, вход сотрудников |
| `players` | player_profiles | карточка игрока: позиции, заявленный и подтверждённый уровень, нога, рост, номер, клуб, девиз, аватар, предпочитаемое время |
| `media` | media_objects | загрузка, проверка типа по содержимому, перекодирование, отдача с отдельного домена |
| `pitches` | pitches | поля, покрытия, обувь, дубли в радиусе 150 м, слияние, модерация |
| `teams` | teams, team_slug_history, team_members, team_join_requests, captaincy_transfers, captain_applications | команды, нейминг, состав, заявки и приглашения, капитанство (заявка, испытательный срок, передача, вице, пропажа капитана, смена города) |
| `matches` | matches, match_slots, match_participants, match_comments, challenges, challenge_responses, position_reservations | матчи трёх типов, видимость, слоты и позиции, запись, лист ожидания, возрастные пороги, расчёт аренды, жизненный цикл, вызовы, сменный вратарь, брони позиций, комментарии |
| `results` | match_reports, match_events, match_votes, match_ratings | протокол в три экрана, подтверждение соперником, окно оспаривания, споры, голосование, оценки, античит протокола |
| `stats` | player_stats_daily, team_stats_daily, team_ratings, team_stat_resets | агрегаты, Elo, паспорт команды, городские таблицы, вес разнообразия состава |
| `reputation` | reliability_snapshots, reliability_reset_requests, payment_notes, payment_flags, payment_flag_disputes | надёжность, реестр «отдал / не отдал», метки спорных расчётов, сбросы |
| `economy` | wallets, ledger_entries, subscriptions, catalog_items, user_inventory, team_inventory, achievements, user_achievements, lootbox_types, lootbox_grants, quests, user_quests, referrals | очки и кредиты (двойная запись), подписки через IAP, косметика, достижения, задания, рефералы, права на платные опции |
| `competitions` | competitions, competition_teams | турниры, сетки, таблицы |
| `predictions` | predictions | прогнозы за заработанные очки |
| `chat` | новые таблицы (спека `chat`) | чат матча и команды, реалтайм |
| `moderation` | abuse_reports, sanctions, anomaly_flags | жалобы, санкции, очереди аномалий |
| `notify` | notifications, notification_preferences, notification_settings, push_tokens | входящие, пуши, письма-уведомления, категории, тихие часы |
| `ads` | ad_placements, ad_dismissals | рекламные блоки |

владения: таблица принадлежит платформе, модули вызывают её API.

### 4.2. Зависимости

Синхронные зависимости — ациклический граф снизу вверх. Направление проверяет archtest
(§11.1), циклы не соберёт компилятор.

```
geo ← identity ← players ← media ← pitches ← teams ← matches ← results
                                              ↑         ↑
economy (права на платные опции) ─────────────┴─────────┘
stats, reputation, competitions, predictions, chat, moderation, notify, ads —
верхний слой: читают нижние модули через интерфейсы, реагируют на события
```

Цепочка задаёт порядок слоёв, а не обязательные связи: модуль может зависеть от любого
модуля левее себя (`pitches` от `geo` и `media`, но не от `teams`). Точный список
разрешённых пар — в карте archtest. Нижний модуль никогда не вызывает верхний синхронно: если `identity` должна узнать о бане,
это делает `moderation` через `identity.IdentityInTx` (§4.3), а не наоборот.

### 4.3. Транзакции между модулями

По умолчанию модули согласуются через события (конечная согласованность). Вызов, который
присоединяется к транзакции вызывающего (транзакция передаётся через `ctx`), разрешён
только здесь:

| Сценарий | Вызывающий → вызываемый | Почему нужна атомарность |
| --- | --- | --- |
| Одобрение заявки на капитанство | `teams` (admin) → `identity.GrantRoleInTx` | заявка одобрена без роли — капитан не может создать команду |
| Бан и снятие бана | `moderation` → `identity.SetStatusInTx` | бан должен действовать в момент решения модератора |
| Запись на матч с платной бронью позиции | `matches` → `economy.ConsumeEntitlementInTx` | слот занят без списания права или право списано без слота |

Список расширяется только правкой этой спеки (или спеки модуля со ссылкой сюда) и страж
§11.3. Начисления очков за закрытый протокол идут событием `results.report_closed`.

### 4.4. События

Имя — `<модуль>.<факт в прошедшем времени>`, версия — поле конверта. Полный каталог с
payload — в спеке каждого модуля; опорные события:

| Событие | Кто слушает |
| --- | --- |
| `identity.user_registered` | players (создать профиль), notify, economy (рефералы) |
| `identity.user_deleted` | все модули с данными пользователя — анонимизация своих строк |
| `identity.city_changed` | teams (вопрос капитану о команде в старом городе) |
| `teams.member_joined`, `teams.member_left` | notify, stats |
| `teams.captain_changed` | notify, stats (сброс по запросу) |
| `matches.published` | notify (составу, городу по фильтрам), stats |
| `matches.roster_changed` | matches (пересчёт долей и статуса `confirmed`), notify («осталось 2») |
| `matches.cancelled` | notify (сразу, мимо тихих часов), reputation, stats |
| `matches.finished` | results (открыть протокол), notify |
| `results.report_closed` | stats, reputation, economy, teams (испытательный срок), competitions, predictions, notify |
| `results.report_disputed` | moderation, notify |
| `moderation.sanction_applied` | teams (пауза команды забаненного капитана), notify |

## 5. Платформа (`internal/platform/*`)

### 5.1. Конвейер запроса

recover → `request_id` → реальный IP (только от доверенных прокси из конфига) → логи и
OTel → лимит тела → таймаут → аутентификация (необязательная, кладёт Principal в `ctx`) →
rate limit → идемпотентность → strict-хендлер. Любая ошибка любого слоя — `problem+json`.

### 5.2. Токены и сессии

- **access** — JWT, подпись EdDSA (Ed25519), 10 минут. Claims: `sub`, `sid`, `aud`
  (`public` | `admin`), `iat`, `exp`, заголовок `kid`. Бинарник принимает только свой `aud`.
  Ключи — из окружения списком: один подписывающий, остальные только проверяющие
  (ротация без разлогина). Алгоритм зафиксирован на сервере, `alg` из токена не читается.
- **refresh** — 256 бит из CSPRNG, в `sessions` хранится SHA-256, срок 60 дней (публичный)
  или 8 часов бездействия / 24 часа максимум (админка). Ротация при каждом использовании.
- **Повтор refresh** отзывает семью (`family_id`) и пишет событие безопасности. Исключение —
  окно 30 секунд после ротации: повтор только что заменённого токена той же сессии выдаёт
  новую пару и отзывает предыдущую ветку (гонка двух вкладок, §7.4).
- Семья привязана к устройству (`sessions.device_id`). Пользователь видит сессии списком
  устройств, «выйти» и «выйти везде».
- **Опасные действия** (смена пароля и почты, удаление аккаунта, передача капитанства,
  роспуск команды) дополнительно сверяют сессию с базой — эффект бана и «выйти везде»
  для них мгновенный; для остального — не позже 10 минут.

### 5.3. Права на ресурс

- Проверяются в `app/` модуля, не в хендлере. Роли актора загружаются у `identity` один раз
  на запрос и кэшируются в `ctx`.
- Невидимый ресурс → `404 <модуль>.not_found` (существование не раскрывается); видимый, но
  запрещённый → `403 <модуль>.forbidden`.
- У каждой ручки с ресурсом есть тест «чужой пользователь» (IDOR).

### 5.4. Идемпотентность

- `Idempotency-Key` обязателен на мутирующих ручках публичного API с аутентификацией;
  контракт объявляет заголовок, страж §11.4 проверяет.
- Ключ — `(user_id, key)`, `request_hash` — SHA-256 от метода, шаблона пути и тела.
- Строка ключа пишется **внутри бизнес-транзакции** (через `ctx`): дубль не закоммитится
  дважды даже при обрыве связи после коммита. Ответ сохраняется после коммита.
- Повтор с тем же телом → сохранённый ответ; тот же ключ с другим телом →
  `422 idempotency.key_reused`; параллельный дубль → `409 idempotency.in_progress`;
  операция закоммичена, а ответ не успел сохраниться → `409 idempotency.replay_unavailable`
  (клиент перечитывает состояние).
- Срок — 24 часа. Анонимные ручки (регистрация, вход) защищены rate limit и уникальностью.

### 5.5. События: outbox → relay → River → inbox

- `events.Publish(ctx, e)` пишет в `outbox` в транзакции из `ctx`; без транзакции — ошибка.
- Конверт: `id` (UUIDv7), `type`, `version`, `aggregate_type`, `aggregate_id`,
  `occurred_at`, `payload`, trace-контекст.
- Подписчики регистрируются в коде при сборке воркера: `(тип события, имя подписчика,
  обработчик)`.
- Relay в воркере: просыпается по `LISTEN/NOTIFY` (страховочный опрос раз в секунды),
  берёт пачку через `FOR UPDATE SKIP LOCKED`, на каждого подписчика ставит **отдельную**
  задачу River той же транзакцией (`InsertManyTx`), отмечает `published_at`. Несколько
  воркеров работают параллельно без выбора лидера.
- Обработчик идемпотентен: в своей транзакции вставляет `event_inbox (subscriber, event_id)`;
  конфликт — событие уже обработано, выходим.
- Порядок между агрегатами не гарантирован; обработчики сверяют версии и `occurred_at`.
- Исчерпавшая попытки задача — «мёртвая», видна в админке, вызывает алерт.
- Опубликованные строки outbox и старые строки inbox чистятся через 30 дней.

### 5.6. Rate limit

- GCRA, одна строка `rate_limits (key, tat)` на ключ, один UPSERT на проверку.
- Ключи: IP, подсеть (/24 для IPv4, /64 для IPv6), почта, пользователь, устройство.
  Политики — в конфиге по классам ручек (вход, регистрация, коды, создание сущностей,
  поиск, комментарии).
- Ответ — `429 ratelimit.exceeded` + `Retry-After`. За интерфейсом: переезд на Valkey —
  замена реализации.

### 5.7. Антибот

- `platform/humancheck.Verifier` — интерфейс. Реализация по умолчанию — PoW по протоколу
  ALTCHA: задача подписана HMAC, содержит срок жизни; использованные решения лежат в
  `humancheck_spent` до истечения срока — повтор не проходит.
- `platform/risk` решает, когда требовать проверку: N неудачных входов на аккаунт или IP,
  всплеск регистраций из подсети, новое устройство, аномальная частота действий.
- Требование — `403 humancheck.required` с задачей в теле; клиент решает и повторяет запрос
  с решением в заголовке.
- Сторонний провайдер (Cloudflare Turnstile, Yandex SmartCaptcha, hCaptcha) — ещё одна
  реализация интерфейса, включается флагом по стране. Доступность и условия провайдеров —
  проверить при подключении.
- Остальные слои: блок-лист одноразовых почтовых доменов (обновляемый файл), скрытое поле и
  минимальное время заполнения на веб-формах, уровни доверия аккаунта (лимиты на заявки,
  комментарии, поля растут с возрастом аккаунта и сыгранными матчами), аномалии — в очередь
  модерации, не автобан.

### 5.8. Ошибки

- `problem+json` с кодом `<модуль>.<ошибка>`; коды объявлены в модуле и перечислены в
  контракте у операции (расширение `x-error-codes`).
- Валидация — единый `400 validation.failed` со списком `{field, code}`.
- `title` — техническая сводка; клиенты показывают текст по `code` из своих локалей.

### 5.9. Прочее

| Механизм | Решение |
| --- | --- |
| ID | UUIDv7 в Go; `DEFAULT gen_random_uuid()` в схеме остаётся страховкой |
| Пагинация | keyset, непрозрачный курсор, `limit` по умолчанию 20, максимум 100 |
| Время | `platform/clock` (подменяется в тестах); хранение в UTC; местное время — по таймзоне города или поля; база таймзон вшита (`time/tzdata`) |
| Серверные тексты | `backend/locales/{ru,en}.json`, ICU-сообщения для писем и пушей; язык — `users.locale`; тест сверки ключей |
| Почта | `platform/mail.Sender`: dev — файлы в `.tools/mail/`, прод — SMTP (провайдер выбирается отдельно); отправка только задачей River |
| Файлы | `platform/blob`: dev — файловая система, прод — S3-совместимое хранилище |
| Наблюдаемость | JSON-логи `slog` без персональных данных (почта маскируется), `request_id` сквозной, OTel-трейсы и метрики по OTLP (в dev выключены), `/healthz` и `/readyz`, метрики очередей |
| Конфиг и секреты | только окружение, валидация на старте, ошибка — процесс не стартует; ключи JWT, HMAC устройств, PoW, шифрования TOTP и cookie поддерживают ротацию списком |
| Фича-флаги | существующий `platform/flags`, проверка в `app/`; выключено → `403 feature.disabled` |
| Кэш | лента города — в памяти процесса на 60 с со схлопыванием промахов (singleflight); это производные данные, принцип «API без состояния» не нарушен; для публичных страниц — `ETag` |
| CORS | выключен: браузер в публичный API не ходит (BFF), Flutter — не браузер |
| Аудит | `platform/audit.Write(ctx, entry)` в транзакции из `ctx` |

## 6. Изменения доменных правил

Правки вносятся в `docs/01-домен-и-правила.md` и `docs/02-архитектура.md` (§14).

### 6.1. Вход и капитанство

- Вход — почта + пароль. Пароль: argon2id (минимум по OWASP: m = 19 MiB, t = 2, p = 1;
  параметры в конфиге, при входе хэш пересчитывается, если параметры выросли), длина от 10
  символов без правил состава (NIST SP 800-63B), проверка по встроенному списку
  распространённых паролей.
- Неудачные входы — нарастающая задержка и PoW, без постоянной блокировки аккаунта (иначе
  чужой аккаунт можно заблокировать перебором). Ответ одинаковый для «нет почты» и «неверный
  пароль».
- Восстановление — код из письма; после смены пароля отзываются все сессии. Смена почты —
  код на новую почту и уведомление на старую.
- Условия заявки в капитаны: подтверждённая почта, возраст не ниже порога страны,
  заполненный профиль, нет активных санкций, не капитан другой команды в этом городе,
  затем ручное одобрение модератором. Телефон — необязательный контакт в заявке, модератор
  видит его как неподтверждённый. Подтверждение телефона — отдельный канал за интерфейсом,
  включается без переделки, если появятся фейки.

### 6.2. Регистрация

- Форма: город (из него страна и порог возраста), дата рождения, почта, пароль, ник.
- Возраст проверяется до отправки кода: младше `min_signup_age` страны — отказ, данные не
  сохраняются.
- До ввода кода данные лежат в `auth_codes` (purpose `signup`, с хэшем пароля); строки в
  `users` нет — неподтверждённые боты не занимают ники и почты. Ник проверяется при вводе и
  повторно в момент подтверждения.
- Код — 6 цифр, хранится хэш, 15 минут, 5 попыток, повторная отправка с нарастающей паузой.

### 6.3. Устройства и связанные аккаунты

| Платформа | Идентификатор | Надёжность |
| --- | --- | --- |
| iOS | Apple DeviceCheck (переживает переустановку) + App Attest (запрос из настоящего приложения) | высокая |
| Android | Play Integrity + `ANDROID_ID` (переживает переустановку, сбрасывается сбросом устройства) | высокая |
| Веб | cookie устройства | жёсткий лимит невозможен |

- Регистраций с мобильного устройства — не больше 2 за всё время; третья отклоняется с
  причиной и ссылкой на поддержку.
- Входов разными аккаунтами — мягкий лимит: больше N за 30 дней — флаг модератору.
- Веб: лимита нет, работают слои §5.7. Аккаунт с веба при первом входе с мобильного
  привязывается к устройству и учитывается в лимите.
- Аккаунты одного устройства — связанные; модератор видит связь. **Голоса за лучшего игрока
  и оценки между связанными аккаунтами не засчитываются.**
- Идентификаторы хранятся только как HMAC с серверным секретом и используются только против
  злоупотреблений. Политику конфиденциальности согласовать с юристом.
- Роли со скоупом делают второй аккаунт ненужным для «капитан в одной команде, игрок в
  другой» — это один аккаунт.

### 6.4. Поля: тип, покрытие, обувь

- `pitch_kind` — `outdoor`, `indoor` (зал, манеж), `covered`.
- `pitch_surface` — `artificial`, `natural`, `ground`, `parquet`, `asphalt`, `sand` +
  новые `rubber` (резиновая крошка, наливное) и `sport_floor` (синтетика зала: ПВХ,
  полиуретан). Окончательный список — в спеке `pitches`.
- Обувь — чистая функция в `pitches/internal/domain`: (покрытие, тип) → набор классов
  (`fg_sg`, `ag`, `tf`, `ic`, `barefoot_sand` — точный набор в спеке `pitches`). API отдаёт
  ключи, тексты — в локалях клиентов.
- Покрытие, тип и обувь — на карточке матча и в напоминании; в ленте — фильтры по типу и
  покрытию.

### 6.5. Снятые ограничения

Турниры, городские рейтинги, подписки, кредиты, косметика, прогнозы, чат и второй язык
строятся полностью. Выключенное в сиде остаётся за флагами по городам. Для прогнозов,
покупок в сторах и призов турниров спека модуля содержит раздел «нужна юридическая
проверка» — без готовых выводов. Жёсткие правила CLAUDE.md (деньги за аренду не принимаем,
прогнозы только за заработанные очки) не меняются.

## 7. Контракт и HTTP-слой

### 7.1. Разбиение контракта

```
contracts/openapi/
  public/
    root.yaml              info, servers, общие компоненты: Problem, Money, Cursor, заголовки
    <модуль>/paths.yaml    операции модуля, тег = имя модуля
    <модуль>/schemas.yaml
  admin/                   та же структура
  public.yaml              бандл (redocly bundle), коммитится, gen:check сверяет
  admin.yaml               бандл
```

Существующий тест одинаковости схемы `Problem` в двух контрактах сохраняется.

### 7.2. Сборка Go-сервера

- oapi-codegen генерирует типы и strict-интерфейс в `internal/httpapi/{public,admin}/oapi`
  — отдельный пакет, иначе цикл импортов: хендлеры модулей импортируют типы, а сервер
  импортирует хендлеры.
- `httpapi/public.Server` встраивает хендлеры всех модулей. Компилятор ловит
  нереализованную операцию и операцию, реализованную дважды (неоднозначный метод).
- Хендлер переводит `oapi`-типы в DTO модуля и обратно.

### 7.3. Конвенции API

- Пути `/v1/...`, ресурсы во множественном числе, действия — подресурсами
  (`POST /v1/matches/{id}/cancel`); поля `snake_case`.
- Деньги — `{ "amount_minor": int64, "currency": "RUB" }`.
- Время — RFC 3339 в UTC + `timezone` места.
- Enum'ы открытые: клиент обязан переживать незнакомое значение; добавление значения — не
  ломающее изменение.
- В `v1` только добавляющие изменения; CI сравнивает контракт с `main` через `oasdiff`,
  ломающее изменение валит PR; ломать — только в `/v2`. Версии контракта — теги
  `contracts-vX.Y.Z`.
- `GET /v1/app/min-version` — принудительное обновление приложений.

### 7.4. Веб как BFF

- Сессия веба — зашифрованная cookie (AES-GCM, ключ из окружения, ротация списком),
  `HttpOnly; Secure; SameSite=Lax`; внутри access и refresh.
- Типы API-клиента (`openapi-typescript`) — только в серверном коде Next; страж §11.6.
- Обновление токена схлопывается в BFF на сессию; в API — окно 30 секунд (§5.2).
- IP клиента — `X-Forwarded-For` от Next; API доверяет заголовку только от адресов из
  списка доверенных прокси. Метка устройства браузера — заголовок `X-WF-Device`.
- CSRF: `SameSite=Lax` + встроенная проверка Origin в server actions; свои route handlers,
  меняющие данные, проверяют Origin явно.

### 7.5. Клиенты

TS-типы для веба и админки — из бандлов. Dart — для wf-native, из того же бандла.

## 8. Воркер (`cmd/worker`)

### 8.1. Очереди River

| Очередь | Что в ней |
| --- | --- |
| `events` | доставка событий подписчикам |
| `lifecycle` | переходы матчей, окна протокола и голосования |
| `notify` | пуши и письма-уведомления, с ограничением скорости |
| `mail` | транзакционные письма (коды, сброс пароля) — отдельно от рассылок |
| `stats` | ночные пересчёты |
| `media` | обработка загрузок |
| `maintenance` | чистка и сроки |

Конкурентность каждой очереди — в конфиге.

### 8.2. Жизненный цикл матча

- При публикации и переносе ставятся отложенные задачи: старт → `live`, конец →
  `awaiting_report`, конец + 72 ч → `expired`, напоминания за 24 ч и 2 ч, напоминания о
  протоколе через 1 ч (капитану) и 12 ч (капитану и вице).
- Задача при выполнении перечитывает матч и сверяет версию и время; устаревшая после
  переноса или отмены ничего не делает — старые задачи не удаляются, гонки нет.
- Страховочный обход раз в 5 минут переводит просроченные матчи.
- `scheduled → confirmed` — по событию `matches.roster_changed`, не по времени.

### 8.3. Периодические задачи

- Ночной пересчёт статистики, надёжности и паспорта — в местные 03:00 каждого города
  (запуск каждый час, выбор городов по таймзоне).
- Окна: 24 ч на оспаривание pickup-протокола → зачёт; 24 ч на голосование → лучший игрок
  (меньше трёх голосов — не присуждается).
- Сроки: заявки в команду (30 дней), вызовы, карантин ников (90 дней), метки спорных
  расчётов (90 дней), неактивность капитана (60 дней), подписки (сверка со сторами).
- Чистка: `idempotency_keys`, `rate_limits`, `auth_codes`, сессии, outbox, `event_inbox`,
  `humancheck_spent`.

### 8.4. Уведомления

- Тихие часы — по таймзоне получателя, задача откладывается до их конца; отмена матча —
  сразу.
- Пик: ограничение скорости на провайдера, случайный сдвиг в пределах минуты.
- Одно напоминание о матче на человека, даже при повторной доставке события.

### 8.5. Конвенции задач

Каждая задача идемпотентна, аргументы версионированы, есть таймаут и лимит попыток;
уникальность по (вид, сущность) — средствами River.

## 9. admin-api

- **Контур:** отдельный бинарник, порт и домен; токены `aud=admin`; refresh — 8 часов
  бездействия, 24 часа максимум.
- **Кто входит:** пользователи с ролью `admin` (глобально) или `city_moderator` (город).
  Остальным при верном пароле — тот же ответ, что при неверном.
- **Вход:** почта + пароль + обязательный TOTP. Первый вход — сначала настройка TOTP.
  Секрет зашифрован AES-GCM (ключ из окружения), повтор кода из того же окна запрещён,
  10 одноразовых кодов восстановления хэшами. Passkeys — позже, интерфейс второго фактора
  готов.
- **Сессия — cookie:** админка — статика без BFF, admin-api ставит
  `HttpOnly; Secure; SameSite=Strict`; админка и API на одном origin через реверс-прокси
  (в dev — прокси Vite, `WF_ADMIN_API_ORIGIN`); CSRF — double-submit токен в `X-WF-CSRF` +
  проверка Origin.
- **Сеть:** аллоулист IP из конфига, в проде включён.
- **Права:** роль и скоуп; модератор видит только свои города. Матрица «действие → кто» —
  в admin-части спеки каждого модуля, тест прав на каждую ручку.
- **Аудит:** каждое изменяющее действие — `audit_log` в той же транзакции (кто, роль,
  действие, объект, было/стало, причина, IP, user-agent). Чтение чувствительного (почта,
  телефон, связанные аккаунты, переписка в жалобе) тоже аудируется.
- **Разрушающие действия** (бан, удаление, сброс ника, смена капитана, слияние полей):
  сервер сверяет поле `confirm` с ником цели; причина из списка + комментарий; бан и
  удаление создаются отложенными на 60 секунд (задача River), «отменить» снимает их до
  исполнения.
- **Разделы MVP:** очередь капитанов; очередь полей (карта, похожие, слияние); жалобы и
  споры, управление матчем в спорной ситуации; пользователи (поиск с лимитами, бан и
  разбан, сброс ника, смена капитана, связанные аккаунты); города (статусы, модераторы);
  фича-флаги; дашборд здоровья; аудит-лог; «мёртвые» задачи.
- **Роли БД:** наименьшие привилегии — `api` не видит `staff_*`; в `audit_log` у всех
  ролей только `INSERT`; `worker` не трогает `credentials`. Гранты — в provisioning-SQL
  (`deploy/`), один для dev и прода.

## 11. Тестирование и стражи

### Тесты по слоям

| Слой | Как |
| --- | --- |
| `domain/` | табличные тесты; деньги — property-based (сумма долей = аренда, стабильный порядок остатка) |

| Гонки | два капитана на одно поле, двое на последний слот, две вкладки обновляют refresh — параллельно на реальной базе |
| Безопасность | JWT с чужим `aud`, `alg=none`, просроченный; повтор PoW и TOTP; rate limit |

### Стражи (каждый проверяется подсадкой бага)

1. **Импорты модулей** (archtest): у чужого модуля — только корневой пакет; направление —
   по графу §4.2; граница админки — как сейчас.
2. **Владение таблицами:** SQL каждого модуля разбирается парсером; запрос к чужой таблице —
   падение; таблица в схеме без владельца — падение.
3. **Транзакции между модулями:** ссылки на интерфейсы `*InTx` — только из списка §4.3
   (анализатор на `go/packages`).
4. **Контракт:** `Idempotency-Key` у мутирующих ручек; коды ошибок задокументированы; тег
   операции совпадает с модулем-реализатором; `oasdiff` против `main`.
5. **Локали:** `backend/locales/{ru,en}` — одинаковые ключи; для каждого кода ошибки
   контракта есть `errors.<код>` в локалях веба и админки.
6. **Веб:** клиентский бандл не импортирует API-клиент (ESLint).
7. **Роли БД:** `api` не читает `staff_*`; `audit_log` не изменяется.
