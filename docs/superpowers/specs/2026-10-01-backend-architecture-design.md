# Архитектура бэкенда — дизайн

Дата: 2026-10-01. Статус: ревью пройдено (одна волна правок), на просмотре у пользователя.
Этап: архитектура Go-бэкенда целиком — модули и их границы, общие механизмы платформы,
контракт, воркер, admin-api, стражи и порядок реализации. Каждый модуль после этой спеки
получает свой цикл спека → план → код; план этой спеки — «фундамент» (§13, пункт 0).

## 1. Цель и критерий готовности

Бэкенд строится как модульный монолит, который выдерживает весь продукт из `docs/01` и
`product/03` без переделки основы: каждый модуль можно понять, протестировать и вынести
в отдельный сервис заменой реализации интерфейса.

Этап «фундамент» (план этой спеки) готов, когда:

1. все механизмы §6 реализованы в `internal/platform/*` и покрыты тестами;
2. все стражи §12 работают и каждый проверен подсадкой бага;
3. контракт разбит по модулям, бандл собирается, `gen:check` сверяет бандл и Go-код;
4. событие, записанное в outbox тестовым модулем, доходит до двух подписчиков через relay
   и River, повтор доставки не задваивает обработку, устаревшая версия агрегата
   отбрасывается — сквозной тест на реальной базе;
5. `cmd/api`, `cmd/admin-api`, `cmd/worker`, `cmd/migrate` собраны на новой платформе,
   `./task dev` работает;
6. документация обновлена (§15).

## 3. Модуль изнутри

```
backend/internal/<модуль>/
  <модуль>.go      публичный API: интерфейс Service, DTO, ошибки, конструктор
  events.go        события, которые модуль публикует, — контракт для подписчиков
  intx/            интерфейс методов из списка §4.4 (если есть); транзакция — явный параметр
  internal/
    domain/        чистые правила без БД, HTTP и часов: инварианты, расчёты, переходы состояний
    app/           сценарии: права, транзакция, outbox, вызовы других модулей
    store/         sqlc-пакет <модуль>db + репозиторий поверх него
  httpapi/         хендлеры своей части публичного API (тип oapi ↔ DTO модуля)
  admin/           хендлеры admin-api; сценарии — в app/, admin/ только вызывает их
  subscribers/     обработчики чужих событий
  jobs/            задачи River модуля
  queries/         SQL модуля
```

- Чужой `internal/` не импортируется — запрещает компилятор Go.
- Другой модуль импортирует только корневой пакет (интерфейс, DTO, события) и, если он в
  списке §4.4, подпакет `intx`. Не `httpapi`, не `admin`, не `jobs`.
- `domain/` не импортирует ничего, кроме стандартной библиотеки и `domain/` своего модуля.
  Время передаётся аргументом.
- Логика, которую исполняет воркер (отложенный бан, удаление), живёт в `app/`, а не в
  `admin/`: `cmd/worker` не может импортировать пакеты с сегментом `admin`.
- Публичный API модуля не знает о HTTP: его можно вызвать из воркера или другого транспорта.
- Модуль без правил (справочник) может не иметь `domain/` — пустые слои не создаются.
- Новый модуль — новый элемент `sql` в `backend/sqlc.yaml` с `omit_unused_structs: true`;
  общие enum'ы схемы (`match_format`, `player_position` и др.) через `overrides`
  отображаются на типы `internal/platform/dbtypes`, чтобы модули не плодили свои копии.

### 4.2. Чтение чужих данных

Главный запрос продукта — лента города — фильтрует матчи по типу и покрытию поля,
возрасту и уровню: это JOIN `matches`, `pitches`, `teams`, профилей и `city_settings`.
Ночные пересчёты `stats` и `reputation` читают протоколы и составы массово. N вызовов
через интерфейсы здесь не работают, поэтому чтение устроено так:

- **Экспортированные представления.** Владелец публикует SQL-представления — свой
  контракт чтения: `<модуль>_read_<имя>` (например, `pitches_read_public`,
  `matches_read_feed`). Представление стабильно: удалить или переименовать колонку — то
  же, что сломать API модуля. В карте владения представление помечено как
  экспортированное.
- **Страж §12.2** разрешает чужому модулю только `SELECT` из экспортированных
  представлений. Прямое чтение чужой таблицы и любая запись в чужое — падение.
- **Проекции** — когда представления мало (горячий путь, вынос модуля в сервис):
  модуль держит у себя денормализованную копию, которую поддерживают события владельца.
  Вводится спекой модуля, не по умолчанию.
- Права на чтение проверяет читающий модуль по данным из представления; приватное
  (дата рождения, почта) в экспортированные представления не попадает — только
  производные («подходит по возрасту на дату матча», `age_years()` внутри представления).

### 4.3. Зависимости

Синхронные зависимости — ациклический граф. Цепочка задаёт порядок слоёв, а не
обязательные связи: модуль может зависеть от любого модуля левее себя. Точный список
разрешённых пар — в карте archtest (§12.1), циклы не соберёт компилятор.

```
geo ← identity ← media ← economy ← players ← pitches ← teams ← matches ← results
верхний слой: stats, reputation, competitions, predictions, chat, moderation, notify, ads —
читают нижние модули через интерфейсы и представления, реагируют на события
```

Правила, вытекающие из доменных требований:

- **Санкции.** Решение о санкции принимает `moderation` (верхний слой), а действует она
  в нижних модулях. `moderation` спускает итог в `identity` через
  `identity/intx.SetRestrictionsInTx`: статус аккаунта и блокировки возможностей
  (`create_match`, `comment`, `captain`, …) в `user_restrictions`. Нижние модули читают
  ограничения из Principal (§6.3), к `moderation` не обращаются.
- **Слияние полей.** `pitches` отмечает дубль `merged_into_id` и публикует
  `pitches.merged`; подписчик в `matches` перевешивает матчи на основное поле. Матч,
  который при переносе нарушил бы `matches_no_pitch_overlap`, остаётся на старом поле и
  уходит модератору флагом — без автоотмены.
- **Экономика ниже команд и матчей.** `economy` не вызывает `players`, `teams`,
  `matches`. Покупку командного предмета оркестрирует `teams` (проверяет капитана, затем
  `economy/intx.DebitInTx`). Аватары и гербы — предметы каталога `economy`; загрузка
  своих изображений — `media`.
- **Смена города.** Сценарий смены города — в `teams`: ручка `PATCH /v1/me/city`
  реализуется модулем `teams`. Он проверяет капитанство в старом городе, требует один из
  трёх ответов из `docs/01` (остаться удалённо, передать вице, пауза), применяет его и
  меняет город через `identity/intx.ChangeCityInTx` — в одной транзакции.

### 4.4. Транзакции между модулями

По умолчанию модули согласуются через события. Вызов, который выполняется в транзакции
вызывающего, разрешён только здесь; метод лежит в подпакете `<модуль>/intx` и принимает
транзакцию **явным параметром** (`tx pgx.Tx`).

| Сценарий | Вызывающий → вызываемый |
| --- | --- |
| Одобрение заявки на капитанство (роль `captain` со скоупом `city`) | `teams` → `identity/intx.GrantRoleInTx` |
| Отзыв капитанского допуска | `teams` → `identity/intx.RevokeRoleInTx` |
| Санкции и их снятие (статус, блокировки возможностей) | `moderation` → `identity/intx.SetRestrictionsInTx` |
| Смена города | `teams` → `identity/intx.ChangeCityInTx` |
| Запись на матч с платной бронью позиции | `matches` → `economy/intx.ConsumeEntitlementInTx` |
| Покупка командного предмета | `teams` → `economy/intx.DebitInTx` |
| Ставка прогноза | `predictions` → `economy/intx.DebitInTx` |
| Протокол: явка и самоподтверждение участников | `results` → `matches/intx.SetAttendanceInTx` |
| Протокол принят или истёк: статус матча | `results` → `matches/intx.SetOutcomeInTx` |

- Список расширяется только правкой этой спеки (или спеки модуля со ссылкой сюда) —
  страж §12.3.
- Обычные методы Service **не присоединяются** к транзакции из `ctx`: каждый открывает
  свою. Это исключает невидимое вхождение в чужую транзакцию и самоблокировку через пул.
  В `ctx` транзакцию читают только `events.Publish` и `audit.Write`; идемпотентность получает
  её аргументом хука `db.WithTxHook` (§6.4), а не из `ctx`.
- Начисления очков за протокол — событием `results.report_closed`.

### 4.5. Роли и права на команду

Один источник истины на каждую роль:

- **Капитан и вице команды** — только `teams.captain_id` и `teams.vice_captain_id`. Права
  на команду (создать матч, вести протокол, принять заявку) спрашиваются у `teams`.
- **`role_assignments`** — глобальные и территориальные роли: `admin` (global),
  `city_moderator` (city), `captain` со скоупом `city` — «допущен к капитанству в этом
  городе» после одобрения заявки. Скоуп `team` не используется; значение `player` не
  выдаётся (игрок — любой пользователь).
- Испытательный срок — свойство капитанского допуска (одобренной заявки), а не команды;
  `teams.is_probationary` становится производным — окончательно в спеке `teams` (§11).

### 4.6. События

Имя — `<модуль>.<факт в прошедшем времени>`. Payload — только идентификаторы и
непрофильные значения; персональных данных (почта, телефон, дата рождения) в событиях
нет. Полный каталог — в спеке каждого модуля; опорные события:

| Событие | Кто слушает |
| --- | --- |
| `identity.user_registered` | notify, economy (рефералы, стартовый аватар) |
| `identity.user_deleted` | все модули с данными пользователя — анонимизация своих строк |
| `teams.member_joined`, `teams.member_left` | notify, stats |
| `teams.captain_changed` | notify, stats |
| `pitches.merged` | matches (перевесить матчи) |
| `matches.published` | notify (составу, городу по фильтрам), stats |
| `matches.roster_changed` | notify («осталось 2») — доли и `confirmed` пересчитываются в транзакции записи, не по событию |
| `matches.cancelled` | notify (сразу, мимо тихих часов), reputation, stats |
| `matches.finished` | results (открыть протокол), notify |
| `results.report_closed` | stats, reputation, economy, teams (испытательный срок), competitions, predictions, notify |
| `results.report_disputed` | moderation, notify |
| `moderation.sanction_applied` | teams (пауза команды забаненного капитана), notify |

### 4.7. Связка статусов матча и протокола

| Протокол (`match_reports.state`) | Матч (`matches.status`) |
| --- | --- |
| нет протокола, < 72 ч после конца | `awaiting_report` |
| нет протокола, 72 ч после конца | `expired` (не учитывается нигде) |
| `submitted` (ждёт соперника или окна 24 ч) | `awaiting_report`, 72 ч больше не считаются |
| `confirmed` или окно 24 ч прошло без 3 возражений | `completed` |
| `disputed` | `awaiting_report` до решения модератора |
| `resolved` | `completed`; учёт в статистике — по решению (`counts_towards_stats`) |

Статус матча меняет `results` через `matches/intx.SetOutcomeInTx` в той же транзакции,
что и протокол.

## 5. Ключевые инварианты конкурентности

- **Запись на последний слот:** транзакция записи берёт `SELECT … FROM matches WHERE id =
  $1 FOR UPDATE`, пересчитывает свободные слоты, доли аренды и статус `confirmed`;
  продвижение из листа ожидания при отказе — в той же транзакции. Источник истины по
  участию — `match_participants`, по позиции на поле — `match_slots`; детали — спека
  `matches`.
- **Два матча на поле** — `EXCLUDE` в базе; код только переводит нарушение в понятную
  ошибку.
- **Перенос и отмена** увеличивают `version` агрегата (§11); отложенные задачи сверяют
  её (§9.2).

## 6. Платформа (`internal/platform/*`)

### 6.1. Конвейер запроса

`request_id` → логи → recover → реальный IP (`platform/peer`, §8.4) → лимит тела → таймаут →
маршрут контракта в `ctx` → аутентификация (необязательная, кладёт Principal в `ctx`) →
валидация запроса по контракту (требование входа — из `security` операции,
`401 auth.unauthenticated`) → rate limit → решение антибота в `ctx` → идемпотентность →
strict-хендлер. Ошибки механизмов — `httpx.ProblemError`: хендлер возвращает их как обычные
ошибки, ответ — их `problem+json`.

- recover стоит внутри логов: паника попадает в лог доступа со статусом 500 и `request_id`.
- Пробы `/healthz` и `/readyz` отвечают до конвейера: без логов доступа и проверки по контракту.
- admin-api — тот же конвейер без аутентификации (вход сотрудников — спека `identity`) и без
  антибота.
- OTel-трейсы (§6.9) в конвейер пока не подключены.

### 6.2. Токены и сессии публичного API

- **access** — JWT, подпись EdDSA (Ed25519), 10 минут. Claims: `sub`, `sid`, `aud=public`,
  `iat`, `exp`, заголовок `kid`. Алгоритм фиксирован белым списком из одного EdDSA
  (golang-jwt `WithValidMethods`, страж `TestParserPinsAlgorithm`); ключ проверки — только по
  `kid` из своего набора. Ключи — из окружения списком (один подписывающий, остальные
  проверяющие); ключей админки у `api` нет — админка JWT не использует (§10). `kid` — первые
  8 байт SHA-256 открытого ключа (`platform/keys.ID`): в окружении только сиды.
- **Проверка сессии на каждый запрос:** одним запросом по `sid` загружаются статус
  аккаунта, `revoked_at` сессии, ограничения и роли (кэш в процессе — не дольше 5 секунд,
  промахи одной сессии схлопываются, размер ограничен — `auth.NewCachedLoader`).
  Бан, «выйти везде» и смена пароля действуют в пределах секунд для всех ручек.
- **refresh** — 256 бит из CSPRNG, в `sessions` хранится SHA-256. Срок скользящий: 60
  дней бездействия, абсолютный максимум семьи — 180 дней. Ротация при каждом
  использовании.
- **Повтор refresh** отзывает семью (`family_id`) и пишет `security_events`.
- **Окно гонки 15 секунд:** если отозванный ротацией токен повторно предъявлен тем же
  устройством (`device_id`) в течение 15 секунд, сервер возвращает **того же** уже
  выданного преемника, без нового ветвления. Преемник хранится зашифрованным
  (ключ — HKDF от предъявленного refresh) только на время окна. Событие безопасности
  пишется и в окне. Украденный токен с другого устройства окна не получает.
- Семья привязана к устройству. Пользователь видит сессии списком устройств, «выйти» и
  «выйти везде».

### 6.3. Principal и права на ресурс

- Principal в `ctx`: пользователь, сессия, устройство, статус, ограничения возможностей,
  глобальные и городские роли.
- Права проверяются в `app/` модуля, не в хендлере; права на команду — через `teams`
  (§4.5).
- Невидимый ресурс → `404 <модуль>.not_found` (существование не раскрывается); видимый, но
  запрещённый → `403 <модуль>.forbidden`; закрытая санкцией возможность →
  `403 identity.restricted` с видом ограничения.
- У каждой ручки с ресурсом есть тест «чужой пользователь» (IDOR).

### 6.4. Идемпотентность

- `Idempotency-Key` обязателен на мутирующих ручках публичного API с аутентификацией и на
  всех мутирующих ручках admin-api; контракт объявляет заголовок, страж §12.4 проверяет.
  Анонимные ручки (регистрация, вход, коды) — исключение: их защищают rate limit и
  уникальность.
- Ключ — `(user_id, key)`; `request_hash` — SHA-256 от метода, **фактического** пути с
  параметрами, query и тела. Колонка `endpoint` хранит фактический путь.
- Строка ключа вставляется **внутри бизнес-транзакции**: дубль не закоммитится дважды даже
  при обрыве связи. Ключ вставляет хук `db.WithTxHook` первой операцией транзакции ручки
  (транзакцию хук получает аргументом); хук узнаёт исход транзакции (`after(committed)`), и
  ответ сохраняется только при коммите.
- Одна закоммиченная транзакция на идемпотентный запрос. После отката ключ снимается, и повтор
  транзакции в том же запросе (например, после `40001`) вставляет его заново; вложенная
  транзакция или вторая после коммита — ошибка (500). Чтения до транзакции — без `db.InTx`.
- Ручка, требующая идемпотентности, обязана выполняться в транзакции: успешный ответ без
  закоммиченной транзакции — 500 и запись в лог.
- Сохраняются ответы со статусом < 500: тело (`jsonb`) и заголовки `Content-Type`,
  `Location`, `ETag` (`response_headers`). Повтор отдаёт ответ с заголовком
  `Idempotency-Replayed: true`. Ответ с телом не-JSON не сохраняется (предупреждение в лог) —
  повтор получит `409 idempotency.replay_unavailable`.
- Повтор с тем же телом → сохранённый ответ; тот же ключ с другим телом →
  `422 idempotency.key_reused`; параллельный дубль ждёт на уникальном индексе не дольше
  `lock_timeout` и получает `409 idempotency.in_progress`; закоммичено, а ответ не успел
  сохраниться → `409 idempotency.replay_unavailable` (клиент перечитывает состояние).
- Бизнес-ошибка (4xx) откатывает транзакцию вместе с ключом — повтор исполняется заново.
  Это ожидаемое поведение.
- Ключ генерирует клиент на одно действие пользователя: в вебе — браузер, BFF передаёт
  его как есть (§8.4).
- Срок — 24 часа.

### 6.5. События: outbox → relay → River → inbox

- `events.Publish(ctx, e)` пишет в `outbox` в транзакции из `ctx`; без транзакции — ошибка.
- Конверт: `id` (UUIDv7), `type`, `schema_version` (версия payload), `aggregate_type`,
  `aggregate_id`, `aggregate_version`, `occurred_at` (время транзакции из базы — `now()`,
  не часы инстанса), `payload`, trace-контекст.
- Подписчики регистрируются в коде воркера: `(тип события, имя подписчика, обработчик)`.
- **Relay в воркере:** просыпается по `NOTIFY` (триггер `AFTER INSERT … FOR EACH
  STATEMENT` на `outbox`) со страховочным опросом; берёт пачку через `FOR UPDATE SKIP
  LOCKED`, на каждого подписчика ставит отдельную задачу River той же транзакцией
  (`InsertManyTx`), отмечает `published_at`. Несколько воркеров работают параллельно.
  `LISTEN` держится на отдельном соединении вне пула (с PgBouncer в transaction mode
  несовместим — учесть в деплое).
- **Обработчик идемпотентен:** в своей транзакции вставляет `event_inbox (subscriber,
  event_id)`; конфликт — уже обработано.
- **Порядок:** между задачами подписчиков не гарантирован даже внутри агрегата. Подписчик в
  режиме `LatestState` хранит последнюю применённую версию агрегата (`event_cursors
  (subscriber, aggregate_type, aggregate_id, version)`) и отбрасывает устаревшие события.
- **Режим доставки** подписчик выбирает явно: `EveryEvent` (счётчики, начисления — применяется
  каждое событие) или `LatestState` (синхронизация состояния — событие со строго меньшей версией,
  чем применённая, отбрасывается; события одной версии применяются все). Курсор ведётся только
  в `LatestState`.
- **Доставка неизвестному подписчику:** задача на подписку, которой нет в реестре этого воркера
  (воркер прежнего релиза при перекрытии выкатки), — обычная ошибка: River повторит с паузой, и её
  возьмёт воркер нового релиза; исчерпав попытки, задача станет «мёртвой» — видна и переигрывается.
  Отменяется (`JobCancel`) только задача на событие, уже удалённое чисткой.
- **Переигровка:** команда `worker events replay --type T --subscriber S --since X` (и кнопка
  в админке) заново раскладывает события из outbox для подписчика; команда в воркере, потому что
  реестр подписчиков знает только он. Нужна, когда подписчик появился позже события или был в
  новом релизе, а раскладывал старый воркер.
  Outbox хранится 30 дней.
- **Удаление аккаунта** не полагается только на событие: каждый модуль с данными
  пользователя имеет сверочную задачу «анонимизировать строки пользователей со статусом
  `deleted`» — она догоняет модули, построенные после удаления.
- Исчерпавшая попытки задача — «мёртвая», видна в админке, вызывает алерт.
- Чистка: опубликованный outbox и старый inbox — через 30 дней.

### 6.6. Rate limit

- GCRA, одна строка `rate_limits (key, tat)` на ключ (`UNLOGGED`-таблица), один UPSERT на
  проверку, вне бизнес-транзакции.
- Ключи: IP, пользователь, устройство — в middleware; почта — в `app/` (middleware не видит
  разобранное тело). Класс ручки — расширение `x-rate-limit` операции контракта (без него —
  `default`); политики классов по ключам IP/пользователь/устройство — `ratelimit.DefaultRules`
  с переопределением строкой `API_RATE_LIMITS` (у admin-api — `ADMIN_RATE_LIMITS`); класс
  контракта без правила — отказ старта.
  Хранилище недоступно — запрос проходит, ошибка в лог (fail-open).
- Строки ключей: `ip:<класс>:<ip>`, `user:<класс>:<uuid>`, `device:<класс>:s:<uuid>`
  (устройство сессии), `device:<класс>:b:<метка>` (метка BFF `X-WF-Device`) — разные
  пространства: метка браузера не совпадёт с устройством сессии. Интервал GCRA усекается до
  микросекунды — точности хранения `timestamptz`.
- Подсеть (/24, /64) — только сигнал для риска, а не жёсткий 429: за CGNAT мобильных
  операторов сидят тысячи людей.
- Ответ — `429 ratelimit.exceeded` + `Retry-After`. За интерфейсом: переезд на Valkey —
  замена реализации.

### 6.7. Антибот

- `platform/humancheck.Verifier` — интерфейс. Реализация по умолчанию — PoW по протоколу
  ALTCHA: задача подписана HMAC и имеет срок жизни; использованные решения лежат в
  `humancheck_spent` (`UNLOGGED`) до истечения срока — повтор не проходит. Решение истекает
  при `now >= expires`.
- Серверная часть ALTCHA своя (`platform/humancheck.PoW`: часы приложения, только SHA-256,
  `kid` ключа в соли, ротация списком); `altcha-lib-go` — только в тестах совместимости с
  виджетом.
- `platform/risk` решает, когда требовать проверку: неудачные входы на аккаунт или IP,
  всплеск регистраций из подсети, новое устройство, аномальная частота действий.
- Требование — `403 humancheck.required` с задачей в теле (поле `challenge`); клиент решает и
  повторяет запрос с решением в заголовке `X-WF-Humancheck`. Middleware только кладёт решение
  в `ctx`; проверяет его `humancheck.Require` в сценарии модуля, когда потребовал риск, — без
  требования решение не тратится.
- Сторонний провайдер (Cloudflare Turnstile, Yandex SmartCaptcha, hCaptcha) — ещё одна
  реализация интерфейса, включается флагом по стране; доступность и условия — проверить
  при подключении.
- Остальные слои: блок-лист одноразовых почтовых доменов (обновляемый файл), скрытое поле и
  минимальное время заполнения на веб-формах, уровни доверия аккаунта (лимиты на заявки,
  комментарии, поля растут с возрастом аккаунта и сыгранными матчами), аномалии — в очередь
  модерации, не автобан.

### 6.8. Ошибки и валидация

- `problem+json` с кодом `<модуль>.<ошибка>`; коды объявлены в модуле и перечислены в
  контракте у операции (расширение `x-error-codes`).
- Strict-сервер oapi-codegen схему не валидирует (`minLength`, `enum`, `format`), поэтому
  запрос проверяется middleware на kin-openapi по контракту.
- Неразбираемый запрос — `400 request.invalid` (как сейчас в `httpx`); нарушение схемы —
  `400 validation.failed` со списком `{field, code}`.
- `title` — техническая сводка; клиенты показывают текст по `code` из своих локалей.

| Конфиг и секреты | только окружение, валидация на старте, ошибка — процесс не стартует; ключи JWT, PoW, шифрования TOTP, cookie и HMAC устройств — списком для ротации |
| Фича-флаги | существующий `platform/flags`, проверка в `app/`; выключено → `403 feature.disabled` |
| Кэш ленты | в памяти процесса на 60 с со схлопыванием промахов (singleflight), **только `public` и `invite_only`**; персональное (свои `team_only`, «я записан») подмешивается после кэша; тест «чужой пользователь» на кэшированном пути; для публичных страниц — `ETag` |
| CORS | выключен: браузер в публичный API не ходит (BFF), Flutter — не браузер; Flutter Web не поддерживается (веб — Next.js) |
| Аудит | `platform/audit.Write(ctx, entry)`: для изменений — в транзакции из `ctx`, для аудита чтения — отдельной короткой вставкой; в `before`/`after` персональные данные маскируются по словам ключа (не по содержимому: свободный текст с ПД в `before`/`after` класть нельзя) |
| Хэширование паролей | argon2id под семафором (ограничение параллельных хэширований — защита от исчерпания памяти анонимными запросами) |

### 6.10. Реалтайм

- Нужен в двух местах: чат и экран заполнения состава перед матчем.
- Браузер не держит токенов и CORS выключен, поэтому соединение открывается так: BFF
  выдаёт одноразовый тикет (`POST /v1/realtime/tickets`, живёт 30 с, привязан к сессии),
  браузер открывает WebSocket напрямую к API с тикетом; API проверяет тикет и `Origin`.
- Между инстансами API — fan-out через `LISTEN/NOTIFY`.
- Детали протокола — спека `chat`.

## 7. Изменения доменных правил

Правки вносятся в `docs/01-домен-и-правила.md` и `docs/02-архитектура.md` (§15).

### 7.1. Вход и капитанство

- Вход — почта + пароль. Пароль: argon2id (минимум по OWASP: m = 19 MiB, t = 2, p = 1;
  параметры в конфиге, при входе хэш пересчитывается, если параметры выросли), длина от 10
  символов без правил состава (NIST SP 800-63B), проверка по встроенному списку
  распространённых паролей.
- Неудачные входы — нарастающая задержка и PoW, без постоянной блокировки аккаунта (иначе
  чужой аккаунт можно заблокировать перебором).
- **Ни один ответ не раскрывает, есть ли аккаунт:** вход — одинаковая ошибка для «нет
  почты» и «неверный пароль», на «нет почты» выполняется фиктивный argon2 для выравнивания
  времени; регистрация и восстановление всегда отвечают «код отправлен», владельцу
  существующего аккаунта уходит письмо «у вас уже есть аккаунт».
- Восстановление — код из письма; после смены пароля отзываются все сессии. Смена почты —
  код на новую почту и уведомление на старую.
- Почта обязательна (`users.email NOT NULL`); CHECK `users_contact_present` снимается.
- Условия заявки в капитаны: подтверждённая почта, возраст на дату заявки не ниже
  `countries.min_signup_age` страны города (решение пользователя 2026-10-01: школьный
  футбол 14–17 организует себя сам; комментарий в `0002_geo.sql:23` о привязке к
  `age_of_majority` устарел — фиксируется в `backend/migrations/README.md`), заполненный
  профиль, нет ограничения `captain`, не капитан другой команды в этом городе, затем
  ручное одобрение модератором. Телефон —
  необязательный контакт в заявке, модератор видит его как неподтверждённый.
  Подтверждение телефона — отдельный канал за интерфейсом, включается без переделки.

### 7.2. Регистрация и профиль

- Форма: город (из него страна и порог возраста), дата рождения, почта, пароль, ник.
- Возраст проверяется до отправки кода: младше `min_signup_age` страны — отказ, данные не
  сохраняются.
- До ввода кода данные лежат в `auth_codes` (purpose `signup`, с хэшем пароля); строки в
  `users` нет — неподтверждённые боты не занимают ники и почты. Ник проверяется при вводе и
  повторно в момент подтверждения.
- Код — 6 цифр, хранится хэш, 15 минут, 5 попыток, повторная отправка с нарастающей паузой.
- Профиль игрока создаётся лениво: первое обращение к `players` создаёт строку с
  умолчаниями (upsert). Сразу после регистрации — шаг онбординга с основной позицией
  (обязательна по `docs/01`); «заполненный профиль» для капитанства включает её.

### 7.3. Устройства и связанные аккаунты

| Платформа | Счётчик регистраций (лимит) | Идентификатор для связывания аккаунтов | Целостность |
| --- | --- | --- | --- |
| iOS | Apple DeviceCheck: два бита на устройство у Apple, переживают переустановку — хватает на счётчик 0–3 | UUID установки в Keychain | App Attest |
| Android | `ANDROID_ID` (переживает переустановку, сбрасывается сбросом устройства) | `ANDROID_ID` | Play Integrity |
| Веб | нет — жёсткий лимит невозможен | cookie устройства | слои §6.7 |

- Регистраций с мобильного устройства — не больше 2 за всё время; третья отклоняется с
  причиной и ссылкой на поддержку.
- Вход разными аккаунтами с одного устройства не блокируется (друг зашёл со своего
  аккаунта); больше N аккаунтов за 30 дней — флаг модератору. Аккаунт, созданный в вебе,
  при входе с мобильного становится связанным с этим устройством.
- **Связанные аккаунты** — аккаунты, которые входили с одного устройства. Связь прямая, не
  транзитивная. Модератор видит связи. **Голоса за лучшего игрока и оценки между
  связанными аккаунтами не засчитываются**; связанность проверяется в момент подсчёта
  (закрытие окна 24 ч), а не в момент голоса.
- Идентификаторы хранятся только как HMAC с серверным секретом. Ротация ключа HMAC
  означает поиск по всем действующим ключам (пересчитать нельзя — исходника нет). Политику
  конфиденциальности согласовать с юристом.
- Роли со скоупом делают второй аккаунт ненужным для «капитан в одной команде, игрок в
  другой» — это один аккаунт.

### 7.4. Поля: тип, покрытие, обувь

- `pitch_kind` — `outdoor`, `indoor` (зал, манеж), `covered`.
- `pitch_surface` — `artificial`, `natural`, `ground`, `parquet`, `asphalt`, `sand` +
  новые `rubber` (резиновая крошка, наливное) и `sport_floor` (синтетика зала: ПВХ,
  полиуретан). Окончательный список — в спеке `pitches`.
- Обувь — чистая функция в `pitches/internal/domain`: (покрытие, тип) → набор классов
  (`fg_sg`, `ag`, `tf`, `ic`, `barefoot_sand` — точный набор в спеке `pitches`). API отдаёт
  ключи, тексты — в локалях клиентов.
- Покрытие, тип и обувь — на карточке матча и в напоминании; в ленте — фильтры по типу и
  покрытию.

### 7.5. Снятые ограничения

Турниры, городские рейтинги, подписки, кредиты, косметика, прогнозы, чат и второй язык
строятся полностью. Выключенное в сиде остаётся за флагами по городам. Для прогнозов,
покупок в сторах и призов турниров спека модуля содержит раздел «нужна юридическая
проверка» — без готовых выводов. Жёсткие правила CLAUDE.md (деньги за аренду не принимаем,
прогнозы только за заработанные очки) не меняются.

### 7.6. Удаление аккаунта

- Строка `users` не удаляется никогда: FK `ON DELETE RESTRICT` (`teams.captain_id`,
  `matches.created_by`, `match_reports.submitted_by`, `competitions.organizer_id` и др.)
  держат её как «надгробие». Статус `deleted`, почта заменяется на необратимую заглушку,
  ник уходит в карантин 90 дней, профиль обезличивается, игрок показывается как
  «Удалённый игрок».
- Каждый модуль анонимизирует свои строки по `identity.user_deleted` и сверочной задаче
  (§6.5).
- `audit_log` только добавляется, поэтому персональные данные в него не пишутся
  (маскирование в `before`/`after`); срок хранения IP — вопрос к юристу.
- Персональных данных нет в payload событий и в аргументах задач River; завершённые задачи
  River чистятся штатно.

## 8. Контракт и HTTP-слой

### 8.1. Разбиение контракта

```
contracts/openapi/
  public/
    root.yaml              info, servers, общие компоненты: Problem, Money, Cursor, заголовки
    <модуль>/paths.yaml    операции модуля, тег = имя модуля
    <модуль>/schemas.yaml
  admin/                   та же структура
  public.yaml              бандл (redocly bundle), коммитится, gen:check сверяет
  admin.yaml               бандл
```

Тест одинаковости схемы `Problem` переводится на бандлы.

### 8.2. Сборка Go-сервера

- oapi-codegen генерирует типы и strict-интерфейс в `internal/httpapi/{public,admin}/oapi`
  — отдельный пакет, иначе цикл импортов: хендлеры модулей импортируют типы, а сервер
  импортирует хендлеры.
- `httpapi/public.Server` встраивает хендлеры всех модулей. Компилятор ловит
  нереализованную операцию и операцию, реализованную дважды (неоднозначный метод).
- Хендлер переводит `oapi`-типы в DTO модуля и обратно.

### 8.3. Конвенции API

- Пути `/v1/...`, ресурсы во множественном числе, действия — подресурсами
  (`POST /v1/matches/{id}/cancel`); поля `snake_case`. Исключение — поля `Problem.challenge`
  в camelCase (`maxNumber`): это формат протокола ALTCHA, так их ждёт виджет.
- GET никогда не меняет состояние — в том числе ссылки-приглашения в матч и команду
  (важно при `SameSite=Lax`).
- Деньги — `{ "amount_minor": int64, "currency": "RUB" }`.
- Время — RFC 3339 в UTC + `timezone` места.
- Enum'ы открытые: клиент обязан переживать незнакомое значение; добавление значения — не
  ломающее изменение. В контракте помечаются `x-extensible-enum` (для генераторов, в том
  числе Dart); `oasdiff` настраивается так, чтобы добавление значения в ответ не считалось
  ломающим.
- В `v1` только добавляющие изменения; CI сравнивает контракт с `main` через `oasdiff`,
  ломающее изменение валит PR; ломать — только в `/v2`. Версии контракта — теги
  `contracts-vX.Y.Z`.
- `GET /v1/app/min-version` — принудительное обновление приложений.

### 8.4. Веб как BFF

- Сессия веба — зашифрованная cookie (AES-GCM, ключ из окружения, ротация списком),
  `HttpOnly; Secure; SameSite=Lax`; внутри access и refresh.
- Типы API-клиента (`openapi-typescript`) — только в серверном коде Next; страж §12.6.
- Обновление токена схлопывается в BFF на сессию; гонку между инстансами Next и записью
  cookie закрывает окно §6.2.
- **IP клиента.** Next сам вычисляет IP клиента от своего доверенного прокси и передаёт
  его заголовком `X-WF-Client-IP`, затирая присланный клиентом. API доверяет заголовку
  только от адресов BFF из конфига **и** при верном общем секрете BFF ↔ API (заголовок,
  ротация списком). Метка устройства браузера — заголовок `X-WF-Device`. Перед API может
  стоять прокси хостинга: `X-Forwarded-For` читается только от адресов `API_TRUSTED_PROXIES` (`ADMIN_TRUSTED_PROXIES` у admin-api),
  справа налево до первого недоверенного; секрет BFF — заголовок `X-WF-BFF-Secret`.
- `Idempotency-Key` генерирует браузер на действие пользователя; BFF передаёт его как есть.
- CSRF: `SameSite=Lax` + встроенная проверка Origin в server actions; свои route handlers,
  меняющие данные, проверяют Origin явно.

### 8.5. Клиенты

TS-типы для веба и админки — из бандлов. Dart — для wf-native, из того же бандла.

## 9. Воркер (`cmd/worker`)

### 9.1. Очереди River

| Очередь | Что в ней |
| --- | --- |
| `events` | доставка событий подписчикам |
| `lifecycle` | переходы матчей, окна протокола и голосования |
| `notify` | пуши и письма-уведомления, с ограничением скорости |
| `mail` | транзакционные письма (коды, сброс пароля) — отдельно от рассылок |
| `stats` | ночные пересчёты |
| `media` | обработка загрузок |
| `maintenance` | чистка, сроки, сверочные задачи, отложенные действия админки |

Конкурентность каждой очереди — в конфиге.

### 9.2. Жизненный цикл матча

- У матча и протокола есть колонка `version`; публикация, перенос и отмена её
  увеличивают.
- При публикации и переносе ставятся отложенные задачи: старт → `live`, конец →
  `awaiting_report`, конец + 72 ч → `expired` (если протокола нет, §4.7), напоминания за
  24 ч и 2 ч, напоминания о протоколе через 1 ч (капитану) и 12 ч (капитану и вице).
- Уникальность задачи River — по (вид, матч, `version`): задачи нового расписания не
  отбрасываются как дубли старых.
- Задача при выполнении перечитывает матч и сверяет `version`; устаревшая ничего не
  делает — старые задачи не удаляются, гонки нет.
- Страховочный обход раз в 5 минут переводит просроченные матчи.
- `scheduled → confirmed` — в транзакции записи (§5), не по времени и не по событию.

### 9.3. Периодические задачи

- **Ночной пересчёт** статистики, надёжности и паспорта: раз в 15 минут выбираются города,
  где местное время уже после 03:00, а местная дата ещё не обработана (отметка последней
  обработанной даты у города). Так не промахиваются пояса с получасовым сдвигом и
  переходы на летнее время.
- **Окна:** 24 ч на оспаривание pickup-протокола → зачёт; 24 ч на голосование → лучший
  игрок (меньше трёх засчитанных голосов — не присуждается).
- **Сроки:** заявки в команду (30 дней), вызовы, карантин ников (90 дней), метки спорных
  расчётов (90 дней), неактивность капитана (60 дней), подписки (сверка со сторами).
- **Чистка:** `idempotency_keys`, `rate_limits`, `auth_codes`, сессии, outbox,
  `event_inbox`, `humancheck_spent`, `staff_invites`.

### 9.4. Уведомления

- Тихие часы — по таймзоне получателя (§6.9), задача откладывается до их конца; отмена
  матча — сразу.
- Пик: ограничение скорости на провайдера, случайный сдвиг в пределах минуты.
- Одно напоминание о матче на человека, даже при повторной доставке события.

### 9.5. Конвенции задач

Каждая задача идемпотентна, аргументы версионированы и без персональных данных, есть
таймаут и лимит попыток; уникальность — средствами River.

## 10. admin-api

- **Контур:** отдельный бинарник, порт и домен.
- **Сессия — непрозрачная, серверная, без JWT.** Случайный токен в httpOnly cookie
  (`Secure; SameSite=Strict`), в `sessions` с `audience=admin` хранится его хэш; каждый
  запрос проверяет сессию в базе. Срок — 8 часов бездействия, 24 часа максимум.
  Компрометация ключей публичного API админку не затрагивает.
- **Один origin:** админка и admin-api — за реверс-прокси на одном домене (в dev — прокси
  Vite, `WF_ADMIN_API_ORIGIN`). CSRF: `SameSite=Strict` + проверка `Origin` + обязательный
  нестандартный заголовок на мутирующих запросах; отдельный double-submit токен не нужен.
- **Кто входит:** пользователи с ролью `admin` (global) или `city_moderator` (city).
  Остальным при верном пароле — тот же ответ, что при неверном.
- **Вход:** почта + пароль + обязательный TOTP.
- **Привязка TOTP — только по приглашению.** Выдача роли сотрудника создаёт
  `staff_invites`: одноразовый код на подтверждённую почту, срок 24 часа, аудит. Привязать
  TOTP можно только с паролем **и** кодом приглашения — кто украл один пароль, свой TOTP
  не привяжет. Сброс второго фактора — только действием другого `admin`, с аудитом и
  новым приглашением.
- **TOTP:** допуск ±1 шаг, `last_used_step` в `staff_mfa` запрещает повтор кода, лимит
  попыток на аккаунт; секрет зашифрован AES-GCM (ключ из окружения); 10 одноразовых кодов
  восстановления хэшами. Passkeys — позже, интерфейс второго фактора готов.
- **Сеть:** аллоулист IP из конфига, в проде включён.
- **Права:** роль и скоуп; модератор видит только свои города. Матрица «действие → кто» —
  в admin-части спеки каждого модуля, тест прав на каждую ручку.
- **Идемпотентность** — как в публичном API (§6.4): двойной клик по «бан» не создаёт две
  санкции.
- **Аудит:** каждое изменяющее действие — `audit_log` в той же транзакции (кто, роль,
  действие, объект, было/стало с маскированием, причина, IP, user-agent). Чтение
  чувствительного (почта, телефон, связанные аккаунты, переписка в жалобе) тоже
  аудируется.
- **Разрушающие действия** (бан, удаление, сброс ника, смена капитана, слияние полей):
  сервер сверяет поле `confirm` с ником цели; причина из списка + комментарий; бан и
  удаление создаются отложенными на 60 секунд (задача River в `maintenance`, логика — в
  `app/` модуля), «отменить» снимает их до исполнения.
- **Разделы MVP:** очередь капитанов; очередь полей (карта, похожие, слияние); жалобы и
  споры, управление матчем в спорной ситуации; пользователи (поиск с лимитами, бан и
  разбан, сброс ника, смена капитана, связанные аккаунты); города (статусы, модераторы);
  фича-флаги; дашборд здоровья; аудит-лог; «мёртвые» задачи и переигровка событий.

### 10.1. Роли БД

Наименьшие привилегии; гранты — идемпотентный `grants.sql`, который `cmd/migrate`
применяет после каждого `up`, `down` и `reset` (таблиц, созданных позже provisioning, иначе не достать);
файл — `backend/internal/platform/grants/grants.sql`. На каждом объекте сначала `REVOKE ALL`,
потом ровно нужное. Широкие умолчания из `deploy/dev/initdb/20_wf.sql` убраны: права
пересчитывает `grants.sql`. Уже инициализированному кластеру и Neon один раз нужен
`ALTER DEFAULT PRIVILEGES … REVOKE` (`docs/deploy-dev.md`).

| Роль | Особенности |
| --- | --- |
| `api` | нет доступа к `staff_*`; `audit_log` — только `INSERT`; `SELECT, INSERT, UPDATE` на `river_job` (уникальная вставка River — `ON CONFLICT DO UPDATE … RETURNING`) — письма с кодами ставятся прямо из запроса |
| `admin` | `audit_log` — `INSERT` и `SELECT`; `staff_*` — полный доступ |
| `worker` | `credentials` — `DELETE` и чтение только столбца `user_id` (условие удаления); хеш пароля недоступен; `audit_log` — только `INSERT`; `river_job` — в т. ч. `MAINTAIN` (ежедневная переиндексация River) |
| все | `UPDATE`/`DELETE` на `audit_log` запрещены (плюс триггер) |

Тест стража §12.7 подключается под ролью `api` и под ролью `worker`.

## 11. Изменения схемы

Применённые миграции не правятся. Каждая спека модуля добавляет свои миграции; план
фундамента — миграции платформы. `ALTER TYPE … ADD VALUE` — отдельной миграцией без
транзакции (`-- +goose NO TRANSACTION`): новое значение нельзя использовать в той же
транзакции.

| Модуль | Изменение |
| --- | --- |
| platform | `outbox`: `id` → uuid (UUIDv7), + `schema_version`, `aggregate_version`, `occurred_at`, `trace`; − `attempts`, `last_error` (повторы ведёт River); триггер `NOTIFY`. Новые: `event_inbox`, `event_cursors`, `rate_limits` и `humancheck_spent` (`UNLOGGED`) |
| identity | `users.email NOT NULL`, − CHECK `users_contact_present`; новые `credentials`, `auth_codes`, `security_events`, `user_identities`, `devices`, `device_accounts`, `user_restrictions`, `staff_mfa` (+ `last_used_step`), `staff_recovery_codes`, `staff_invites`; `sessions` + `device_id`, `audience`, поля окна гонки |
| players | `player_profiles`; игровые поля переносятся из `users` одной миграцией «создать → скопировать → удалить» |
| media | `media_objects`; `pitches.photo_urls`, `catalog_items.asset_url`, `ad_placements.image_url` → ссылки на `media_objects` (в спеках владельцев) |
| pitches | новые значения `pitch_surface` (отдельная миграция) |
| teams | один источник испытательного срока: `captain_applications.is_probationary` vs `teams.is_probationary` — решение в спеке `teams` |
| matches, results | колонка `version` у `matches` и `match_reports`; реестр «отдал / не отдал» — один источник: `payment_notes` (`reputation`) vs `match_participants.paid` — решение в спеке `reputation` |
| chat | новые таблицы — в спеке `chat` |

### Тесты по слоям

| Слой | Как |

### Стражи (каждый проверяется подсадкой бага)

1. **Импорты модулей** (archtest, `go list -deps`, как в `boundary_test.go`): у чужого
   модуля — только корневой пакет и `intx` из списка; направление — по графу §4.3;
   граница админки — как сейчас.
2. **Владение таблицами:** SQL каждого модуля разбирается `wasilibs/go-pgquery` (wasm, без
   cgo, уже зависимость sqlc в `backend/tools/go.mod`); запись в чужую таблицу или чтение
   чужой таблицы (не экспортированного представления) — падение; таблица, представление
   или функция в схеме без владельца — падение.
3. **Транзакции между модулями:** импорт `<модуль>/intx` — только из пар списка §4.4
   (тем же механизмом `go list -deps`).
4. **Контракт:** `Idempotency-Key` у мутирующих ручек (кроме анонимных из списка); коды
   ошибок задокументированы; тег операции совпадает с модулем-реализатором; `oasdiff`
   против `main`.
5. **Локали:** `backend/locales/{ru,en}` — одинаковые ключи; для каждого кода ошибки
   контракта есть `errors.<код>` в локалях веба и админки.
6. **Веб:** клиентский бандл не импортирует API-клиент (ESLint).
7. **Роли БД:** под ролью `api` нельзя прочитать `staff_*` и изменить `audit_log`; под
   `worker` нельзя прочитать `credentials`.
