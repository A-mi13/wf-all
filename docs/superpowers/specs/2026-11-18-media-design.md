## 1. Зачем, цели, границы

### 1.1. Зачем

Картинки нужны полям (найти и оценить поле), каталогу `economy` (аватары, гербы, косметика — монетизация и
достижения), модерации (улики в спорах и жалобах) и поддержке. Спека бэкенда отдала `media` загрузку, проверку типа
по содержимому, перекодирование и отдачу с отдельного домена, а S3-реализацию `platform/blob` — этой спеке. Модуль
стоит в порядке §13 спеки бэкенда перед `economy`: первым его потребителем будут ассеты каталога, затем фото полей.

### 1.2. Цели

| # | Цель | Критерий |
| --- | --- | --- |
| Ц1 | Один механизм на три режима: публичное от людей, закрытое от людей, ассеты сотрудников | §3; владельцы не пишут своей загрузки |
| Ц2 | Тяжёлые файлы не идут через API | клиент грузит прямо в хранилище (§3.1) |
| Ц3 | Наружу — только перекодированное | оригинал не отдаётся; растр (и вшитый в Lottie) перекодирован, метаданные кроме цветового профиля не переносятся (§3.3, §3.6) |
| Ц4 | Тип — по содержимому, не по имени и заголовку | сигнатура и успешное декодирование (§3.3) |
| Ц5 | Закрытое не утекает | отдельный бакет и отдельный адрес без CDN, отдача — подписанной ссылкой после проверки прав владельцем (§3.5, §6.5) |
| Ц6 | Снятое модератором исчезает | удаление файлов задачей в той же транзакции, что решение, и сброс кэша CDN (§3.8) |
| Ц7 | Ничего не копится | брошенные загрузки, отклонённые и откреплённые объекты удаляет чистка (§3.9); квота объёма (§3.11) |
| Ц8 | dev и e2e без облака | FS-эмуляция подписанных ссылок (§6.3) |
| Ц9 | Стенд без хранилища работает | режим `none`: модуль отвечает `503 media.unavailable`, остальное приложение живо (§6.4) |

### 1.3. Не-цели (делают другие)

| Что | Кто |
| --- | --- |
| Кто вправе грузить и куда прикреплять (фото поля, ассет, улика) | модуль-владелец (§2.4) |
| Аватары и гербы как предметы, их выдача | `economy` (каталог, инвентарь) |
| Жалобы на фото, очередь и решение модератора | `moderation` (`abuse_reports`), экраны — владельцы экранов (§3.8) |
| Колонки-ссылки владельцев: `pitches.photo_urls`, `catalog_items.asset_url`, `ad_placements.image_url` | спеки владельцев переводят их на `media_objects` (спека бэкенда §11) |
| Рисование карточки игрока для шаринга | `players`; `media` хранит результат (§3.7) |

### 1.4. Анти-цели (не делаем никогда)

- Не отдаём оригинал файла пользователя — только перекодированные варианты.
- Не храним и не показываем фото людей; не делаем загрузку аватара и своего логотипа команды (М1–М3).
- Не принимаем видео (М8).
- Не публикуем закрытое: улики и скриншоты поддержки не получают публичного адреса и не проходят через CDN.
- Не доверяем `Content-Type`, расширению и размеру, которые назвал клиент: всё перепроверяет воркер.
- Персональные данные — не в ключах хранилища, не в событиях, не в аргументах задач, не в логах.

## 2. Граница модуля

### 2.1. Что в `media`

- билеты загрузки (`media_uploads`): подписанная ссылка на «входящее», срок, предел, намеченный владелец;
- объекты (`media_objects`): цель, состояние, видимость, владелец, кто загрузил;
- конвейер обработки (`media.process`), удаление файлов (`media.purge`), чистка;
- отдача: публичные адреса вариантов, подписанные ссылки на закрытые;
- S3-реализация `platform/blob`, режим `none`, эмуляция подписанных ссылок для dev.

### 2.3. Связь с владельцами: `media/intx` (решение автора спеки)

Всё, что меняет объект на стороне владельца, — в **его** транзакции (у ручки с `Idempotency-Key` — одна
закоммиченная `db.InTx`, `backend-platform.md`):

```go
// media/intx — tx явным параметром (спека бэкенда §4.4)
AttachInTx(ctx, tx, objectID uuid.UUID, owner media.OwnerRef, by media.Uploader) (media.Object, error)
CreateDirectInTx(ctx, tx, staged media.Staged, owner media.OwnerRef, by media.Uploader) (media.Object, error)
DetachInTx(ctx, tx, objectID uuid.UUID, owner media.OwnerRef) error
TakeDownInTx(ctx, tx, objectID uuid.UUID, actor media.Actor, reason string) error
// OwnerRef{Type, ID}; Uploader — игрок (user id) или сотрудник (staff id); Actor — сотрудник или игрок-автор
```

- `AttachInTx`: строка объекта `FOR UPDATE`; годится только `pending_upload` с живым окном «завершить» (§3.1 п. 5)
  или уже прикреплённый **к тому же** владельцу (повтор — без изменений). Отказ (`409 media.object_unavailable`), если
  цель объекта не допускает тип владельца (§2.2), **намеченный владелец билета ≠ `owner`** (I-5), **загрузивший ≠
  `by`**, объект в другом состоянии или у другого владельца. Успех: `uploaded`, вставка задачи `media.process` (River в
  той же tx, `UniqueOpts` по объекту).
- `CreateDirectInTx` — прямая загрузка (сотрудник, система): байты уже лежат во «входящем» (`media.Service.Stage`
  кладёт их **без записи в базу** и отдаёт `Staged{Key, Purpose, Bytes}`), объект создаётся сразу `uploaded` с
  владельцем и задачей. Откат транзакции владельца оставляет только файл во «входящем» — его убирает правило жизненного
  цикла (§3.9).
- `DetachInTx` (автор удалил своё фото, владелец заменил ассет): `detached`, вставка `media.purge` в той же tx — файлы
  удаляются сразу после коммита, откат ничего не теряет. Из конечных состояний (`detached`, `taken_down`, `rejected`)
  и для уже удалённой строки — успех без изменений: подписчик владельца, открепляющий снятое и отклонённое, идемпотентен
  (m3-1).
- `TakeDownInTx` (решение модератора, «заменить»): `taken_down`, аудит `media.object_taken_down` (актор, причина —
  код, не свободный текст), событие, вставка `media.purge` (с адресами для `Purger`) — всё в транзакции решения: жалоба
  не закрывается без снятия и наоборот.
- Чтение — представление `media_read_objects` (§5.4).

## 3. Сценарии

### 3.1. Загрузка игроком (прямая)

1. Клиент вызывает ручку владельца «начать загрузку» (например `POST /v1/pitches/{id}/photos/uploads`, тело
   `UploadRequest`): владелец проверяет права и вызывает `media.Service.NewUpload(ctx, purpose, intendedOwner, by,
   declared)`. Режим `none` — `503 media.unavailable` (§6.4).
2. `media` проверяет заявленные тип и размер (ранний отказ `422`), лимиты и квоту (§3.11), создаёт объект
   `pending_upload` и билет с **намеченным владельцем** и загрузившим (I-5): подписанная ссылка на ключ `<object_id>` в
   бакете входящего, метод, обязательные заголовки, срок 15 мин, предел размера (§3.2). Ответ — `UploadTicket` (§7.1).
   Ответ ручки «начать» хранится идемпотентностью как обычно: ссылка в нём — секрет на 15 минут, повтор с тем же
   ключом отдаёт её же (решение автора спеки, m4).
3. Клиент кладёт байты прямо в хранилище по ссылке (адрес хранилища — §6.5).
4. Клиент вызывает ручку владельца «завершить» (например `POST /v1/pitches/{id}/photos {upload_id}`). Владелец
   **проверяет права заново** (они могли смениться за 15 минут) и в своей транзакции вызывает `AttachInTx`.
5. До транзакции, только если объект ещё `pending_upload`: `HEAD` входящего — файла нет → `409
   media.upload_incomplete` (m1: у уже прикреплённого `HEAD` не нужен — повтор идемпотентен). «Завершить» принимается
   до `expires_at + 1 ч` (окно медленной загрузки, начатой до срока; сравнение строгое, `clock.Clock`), позже — `410
   media.upload_expired` (m2). Билет на другого владельца или от другого загрузившего неотличим от несуществующего:
   без `HEAD` и без `409`/`410`, отказ `409 media.object_unavailable` даёт `AttachInTx` **(план media, 26.11)**.
6. Ответ владельца — его ресурс с `MediaImage` в состоянии `processing`; готовность клиент видит при следующем чтении.

Веб (`apps/web`) грузит так же: «начать» и «завершить» — через BFF, байты — из браузера по билету (CORS входящего —
только origin продукта, `connect-src` веба — адрес хранилища).

### 3.2. Предел размера при прямой загрузке

- Билет — **только подписанный `POST`** с политикой `content-length-range` **ровно** `[declared_bytes,
  declared_bytes]` (клиент называет точный размер; иначе квота по `declared_bytes` обходилась бы заявкой «1 байт»,
  m2-6) и `Content-Type` условием политики. Подписанный `PUT` не используется ни в S3, ни в FS — у клиентов одна
  дорога; `UploadTicket.method` в контракте остаётся открытым enum `PUT | POST`, сервер выдаёт `POST` **(план media,
  26.11, R3: Garage соблюдает `content-length-range`, `PUT` с подписанным `Content-Length` не документирован ни у
  кого)**;
- воркер читает файл одним `Get` через `LimitReader(max+1)`: больше предела — `rejected(too_large)` (m3: `HEAD` до
  чтения — только ранний отказ, клиент мог перезалить файл по живому билету). На S3 перезаливку другого размера по
  живому билету отвергает хранилище; предел воркера держит и обход политики ключом с записью во входящее (у api и
  admin она есть, R2) — `TestMediaE2ES3/size` **(план media, 26.11)**.

### 3.3. Обработка (задача `media.process`, очередь `media`)

Задача вставляется с `UniqueOpts` по `object_id` и явным `ByState`: `available`, `scheduled`, `pending`,
`retryable`, `running` — второй экземпляр не появляется ни при повторе «завершить», ни при перезапуске чисткой, пока
первый ждёт повтора (I-3, R2-I1). `MaxAttempts` задачи — 10.

1. **Захват** — короткая транзакция: строка `FOR UPDATE` (ждать, не пропускать); состояние не `uploaded`/`processing`
   (снято, откреплено, уже готово) — задача завершается успешно. Застали `processing` — прошлый исполнитель **упал**
   (обычная ошибка возвращает объект в `uploaded`, см. ниже): `process_attempts + 1`; `process_attempts ≥ 3` —
   отклонение `processing_failed` по п. 8 (файл, роняющий процесс, не ходит по кругу; m2-3). Иначе `processing`.
   Коммит.
   Обычная ошибка шагов 2–7 (хранилище моргнуло, сбой базы, отмена контекста при остановке воркера) — короткой
   транзакцией на `context.WithoutCancel` с собственным сроком (5 с) `processing → uploaded` и возврат ошибки River
   (повтор с паузой; не удался и откат — объект останется `processing`, и это засчитается как падение — принято, m3-2); последняя попытка River (`MaxAttempts`) — отклонение `processing_failed`.
2. Чтение входящего: `Get` + `LimitReader(max+1)` — больше предела цели → `rejected(too_large)`.
3. Заголовок без полного декодирования: сигнатура — один из входов цели; размеры ≤ предела пикселей (защита от
   «бомбы»); анимированный WebP/APNG — `unsupported_type`; иначе `rejected(unsupported_type | too_many_pixels)`.
4. Полное декодирование с бюджетом памяти, рассчитанным по размерам до декодирования; сбой — `rejected(corrupt)`.
   Ориентация EXIF применяется к пикселям.
5. Проверка содержимого (порт, §8) — у целей, где она включена.
6. Варианты перекодируются из пикселей. Метаданные (EXIF, XMP, GPS, комментарии) **и профиль ICC пользователя** не
   переносятся никогда (R2-I2: иначе произвольные байты профиля шли бы в декодер каждого клиента). Профиль
   распознаётся по содержимому: sRGB или профиля нет — вариант без профиля; Display P3 (снимки iPhone) — в вариант
   вписывается **наш эталонный профиль P3** из сборки, иначе фото выцветает; прочие профили — как sRGB (редкость,
   принят сдвиг цвета). Перевода в sRGB без CMS на чистом Go нет (§13 п. 2) (решение автора спеки). Ключи — `<object_id>/<вариант>.webp` в бакете
   видимости (публичный или закрытый). Запись с `Cache-Control` (§6.2).
   **(План media, 26.11, R6, R8.)** Кодировщик WebP — `github.com/deepteams/webp` (MIT, чистый Go, с потерями и
   альфой, поле ICC; запасной — `gen2brain/vpx` + ручной чанк `ICCP`, последний запасной — §13 п. 2). Ориентация EXIF
   (тег `0x0112` в APP1) и ICC (JPEG APP2 `ICC_PROFILE` с многочастными сегментами, PNG `iCCP`, WebP `ICCP`) —
   **свой разбор** в `media/internal/imaging`: живых библиотек на чистом Go нет. P3 распознаётся по тегу `desc`
   (`Display P3`, без учёта регистра) **и** первичным координатам `rXYZ/gXYZ/bXYZ` в допуске ±0.002 от эталона;
   эталонный профиль — CC0-файл `media/internal/imaging/icc/display-p3.icc` (источник и лицензия — `icc/LICENSE`).
7. **Публикация** — транзакция: строка `FOR UPDATE`:
   - `processing` — строки вариантов, `ready`, событие `media.object_ready`;
   - `ready` (другой исполнитель успел раньше; ключи и байты те же) — ничего, задача завершается;
   - `detached`/`taken_down`/`rejected` (снято или откреплено во время обработки, I-4) — вставляется `media.purge`
     по записанным ключам (файлы удаляются, кэш CDN сбрасывается). **Только в этих трёх состояниях** (R2-I1).
   Коммит, затем удаление входящего.
8. Отклонение (шаги 2–5, захват при `processing_failed`, последняя попытка River): транзакция с проверкой состояния
   (`uploaded`/`processing`) — `rejected` с кодом, событие `media.object_rejected`, `media.purge` входящего и
   записанных ключей (m2-2).

Идемпотентность: повтор задачи после сбоя начинается с шага 1 и перезаписывает те же ключи (одинаковые байты), строки
вариантов вставляются только на шаге 7 вместе со сменой состояния.

HEIC/HEIF: клиент переводит в JPEG до загрузки; найдётся рабочий декодер без cgo (§13 п. 2) — HEIC добавляется во входы
`pitch_photo` и закрытых целей (по М12 сервер всё равно хранит WebP). **(План media, 26.11, R7.)** HEIC **не
принимается**: единственный декодер на чистом Go (`gen2brain/h265`) несёт вопрос патентов HEVC — к юристу; до ответа
вход HEIC в целях не объявляется.

Память: пик ≈ (пиксели × 4 Б × 2 на ресайз) × исполнители очереди `media`; `WORKER_QUEUE_MEDIA` выбирается так, чтобы
пик при 40 Мп укладывался в память воркера (критерий §13 п. 2; стенд — встроенный воркер, очередь `media` там пуста
при `none`). **(План media, 26.11, спайк Task 1.)** Формула занижает пик в 1,4–2,4 раза (промежуточный буфер ресайза
`x/image/draw`). **(Финальное ревью, 27.11.)** У JPEG до декодирования проверяется бюджет декодера — не больше 8 Б на
пиксель предела цели (выборка, число компонент, коэффициенты прогрессивного), поэтому пик на 40 Мп — до ≈ 0,6 ГиБ на
исполнителя; худший принятый вход — PNG 16 бит Adam7, ≈ 0,9 ГиБ. **(Перепроверка финального ревью, 27.11.)** При
`WORKER_QUEUE_MEDIA=2` — до ≈ 1,2 ГиБ у JPEG, а два PNG 16 бит Adam7 разом дают пик памяти рантайма ≈ 1,84 ГиБ на голом
процессе (сверху River, пулы pgx, relay и прочие очереди): воркеру своего сервера — не меньше 2,5 ГиБ памяти, меньше —
`WORKER_QUEUE_MEDIA=1`.

### 3.4. Отдача

- Публичное: `media.Service.PublicURL(key)` = `*_MEDIA_PUBLIC_BASE_URL` + ключ (владельцы адресов не склеивают);
  `Cache-Control: public, max-age=86400`, `X-Content-Type-Options: nosniff`, `Content-Type` — из варианта.
- Закрытое — §3.5. Режим `none` — адресов нет (`MediaImage.variants` пусты, состояние `unavailable` не нужно:
  объектов в `none` не бывает).

### 3.5. Закрытые файлы

- Бакет закрытого без публичного доступа; публичного адреса у закрытого объекта нет ни на каком шаге (страж §12).
- Показ: ручка владельца проверяет права (модератор города, сторона спора, сотрудник поддержки) и вызывает
  `media.Service.PrivateURL(ctx, objectID, variant)` → подписанный `GET` на 5 минут на **адрес хранилища** (не домен
  медиа и не CDN, §6.5) с `response-cache-control=private, no-store`. Ответ ручки — `Cache-Control: no-store`.
- Аудит чтения закрытого — у владельца (`audit.WriteRead`).
- **(План media, 26.11, ревью Task 11.)** CSP админки (`img-src`) содержит только origin домена медиа
  (`*_MEDIA_PUBLIC_BASE_URL`), но не адрес хранилища: при `s3` закрытые картинки в админке по подписанной ссылке не
  покажутся (при `fs` адрес api и домен медиа совпадают). Добавить origin `ADMIN_BLOB_S3_PUBLIC_ENDPOINT` в `img-src` —
  требование к первому владельцу закрытых картинок в админке (модерация, поддержка), не к плану `media`.

### 3.6. Ассеты сотрудников (admin-api)

- Операция владельца в admin-api (например «ассет предмета»): `multipart/form-data`, предел 5 МБ (у операции —
  исключение из общего `httpx.MaxBodyBytes` 1 МиБ, m6). Ход: `media.Service.Stage(ctx, purpose, r, declared)` кладёт
  байты во «входящее» без записи в базу → транзакция владельца с `CreateDirectInTx` (I-2). Тот же конвейер §3.3.
  **(План media, 26.11, R16.)** Исключение из лимита тела — `httpx.LimitBody(n, except ...httpx.BodyLimit)`,
  `BodyLimit{Method, Prefix, Max}`: совпали метод и префикс пути — свой предел, иначе общий (`chi` запрещает `Use`
  после маршрутов, поэтому не middleware на маршруте). Пользуются FS-путь `POST /_blob/in` (максимум реестра + 64 КиБ на
  поля формы) и тестовая прямая загрузка admin-api (5 МиБ); операции владельцев (ассеты `economy`) добавят свой
  `BodyLimit` в своих планах.
- Причина не грузить из браузера напрямую: CSP admin-api (`connect-src 'self'`, `httpapi/admin/static.go`) и
  маленькие файлы. Показ ассетов в админке — `img-src` с доменом медиа (правка CSP в плане).
- «Заменить» фото поля модератором: `Stage` + в транзакции решения `TakeDownInTx` старого и `CreateDirectInTx` нового
  (загрузивший — сотрудник, проверка содержимого — как у игрока).
- **Lottie** (М14, цель `catalog_animation`) — разбор в **схему-разрешение** (I-8): из JSON переносятся только
  известные поля слоёв, форм, трансформаций и ключевых кадров; всё прочее выбрасывается при ужатии. Отказ
  `unsafe_animation`, если:
  - есть выражения (поле `x` у свойств — JavaScript);
  - есть ссылки на внешние файлы: `assets[].u`/`p` не `data:`, `fonts.list[].fPath`/`origin`, аудио-слои (`ty` 6);
  - ~~текстовые слои, которым нужен шрифт: допускается только текст глифами из `chars` (контуры вшиты)~~ —
    **(план media, 26.11, Task 8)** строже: любой текстовый слой (`ty` 5) — отказ (в схеме LAC 1.0.1 текста нет);
    `fonts` и `chars` не переносятся, ссылка на файл шрифта (`fonts.list[].fPath`/`origin`) — отказ; текст в анимации —
    только формами (переводится в контуры при экспорте);
  - `fr ≤ 0`, длительность `(op − ip) / fr` > 10 с, глубина JSON > 64, размер > 1 МБ.
  
  Вшитые картинки (`data:image/png|jpeg|webp`) декодируются и **перекодируются в WebP** тем же конвейером (пределы —
  256 КБ и 4 Мп на картинку); `data:image/svg+xml` и прочие типы — отказ. На выходе — `application/json`.
- Статичная WebP к анимации обязательна (М14): отдельный объект `catalog_asset`, связь держит `economy`. Плеер в
  админке — lottie-web из своей сборки (`script-src 'self'`) без выражений (проверить сборку без `unsafe-eval`, §13).

### 3.7. Генерируемое системой

`players` рисует карточку и вызывает `Stage` + `CreateDirectInTx` в своей транзакции (загрузивший — система: оба поля
«кто загрузил» пусты). Тот же конвейер (перекодирование — да, проверка содержимого — нет).

### 3.8. Снятие (жалоба, решение модератора, удаление владельцем)

- Жалоба на фото поля — `moderation` (`abuse_reports`, новая цель — в спеке `moderation`); счётчик жалоб и решение
  «оставить / удалить / заменить» — экран модерации (М10). **Порядок:** `pitches` (§13 спеки бэкенда, п. 6) идёт раньше
  `moderation` (п. 11) — приём жалоб на фото должен появиться не позже фото полей; это решает спека `pitches` или
  `moderation`.
- Снятие — `TakeDownInTx` в транзакции решения (§2.3); файлы удаляет `media.purge` сразу после коммита, он же
  вызывает `Purger` (сброс кэша CDN по адресам вариантов) и повторяется при сбое (River). Без CDN снятое исчезает
  сразу; с CDN без сброса — не позже `max-age` суток.

### 3.9. Чистка (задачи `maintenance` воркера)

| Что | Срок | Действие |
| --- | --- | --- |
| `pending_upload`, окно «завершить» прошло (`expires_at + 1 ч`) | входящее — сразу после окна; строка — через 24 ч от `created_at` | входящее — `Delete`; строки объекта и билета удаляются только у строки старше суток: суточная квота байт считается по строкам, ранняя чистка вернула бы её **(план media, 26.11, Task 6, 10)** |
| `uploaded`/`processing` дольше 1 ч | — | `media.process` вставляется заново (`UniqueOpts` — дубля нет); `process_attempts` ограничивает круги (§3.3) |
| `detached`, `taken_down` | 24 ч после `ended_at` | строки удаляются (файлы уже удалил `media.purge`; сверка ключей — `Delete` идемпотентен) |
| `rejected` | 30 сут после `ended_at` | строки удаляются (владелец успевает показать «не принято» и открепить; ссылка владельца без FK — §2.4) |
| входящее | 1 сутки | правило жизненного цикла бакета (+ сверка чисткой по префиксу без строки) |

Пачками `SKIP LOCKED` (чистка уступает сценарию), граница строгая; удаление файлов идемпотентно.

### 3.10. Удаление аккаунта

Фото полей остаются (они о поле); подписчик события удаления аккаунта (`identity`) обнуляет `uploaded_by_user` у
объектов аккаунта — CHECK допускает «не больше одного загрузившего» (I-6). Закрытые вложения хранит и удаляет по своим
срокам владелец. Незавершённые билеты аккаунта удаляются (`pending_upload`).

### 3.11. Лимиты и квота

| Класс | Ключ | Значение (решение автора спеки) |
| --- | --- | --- |
| `media_upload` (билеты) | игрок | 30 в час, 100 в сутки |
| `media_upload` | IP | 60 в час |
| незавершённые билеты | игрок | ≤ 5 одновременно (`429 media.too_many_pending`); подсчёт под `pg_advisory_xact_lock` по загрузившему (m5) |
| объём | игрок | ≤ 200 МБ в сутки по `declared_bytes` выданных билетов (`429 media.quota_exceeded`) |
| ассеты сотрудника | сотрудник | общий класс admin-api |

Суточные пределы игрока — классы `media_upload_day` и `media_bytes_day` (`ratelimit.DefaultRules`), и
`API_RATE_LIMITS` действует на них так же, как на классы конвейера. Суточный билет засчитывается только после
коммита: отказы (`429` по незавершённым, квоте или самому счёту) его не тратят. Параллельные «начать» у границы
превышают суточный счёт не больше чем на 4 (незавершённых ≤ 5) **(план media, 26.11)**.

Диск своего хранилища: тревога при заполнении тома > 80 % — в `deploy/server/README.md` (порядок проверки) и в
наблюдаемости, когда она появится.

## 4. Состояния объекта

```
pending_upload ──AttachInTx──▶ uploaded ──▶ processing ──▶ ready
      │                           │              │            │
      │(окно прошло: чистка)      ├──────────────┴──▶ rejected (воркер)        DetachInTx из конечных — без изменений
      ▼                           │
   удалён        DetachInTx / TakeDownInTx из uploaded | processing | ready ──▶ detached | taken_down
CreateDirectInTx ──▶ uploaded
```

**(План media, 26.11, Task 5.)** Кроме диаграммы: `processing → processing` (захват, заставший `processing`, —
прошлый исполнитель упал, `process_attempts + 1`, §3.3 п. 1) и `processing → uploaded` (откат после обычной ошибки
шагов 2–7). Из `uploaded` — ещё `rejected`, `detached`, `taken_down`; из `ready` — `detached`, `taken_down`.

Переходы проверяет `domain`; CHECK базы — на допустимые пары «состояние — заполненные поля» (`owner_*` заданы у всех,
кроме `pending_upload`; `ended_at` — у `detached`/`taken_down`/`rejected`; `reject_code` — только у `rejected`;
`uploaded_at` — у всех, кроме `pending_upload` **(план media, 26.11)**).

## 6. Хранилище (`platform/blob`)

### 6.1. Интерфейсы

`Store` дополняется понятием бакета (m7): `Bucket(name) Store` — ключи без префикса бакета; плюс

- `Put(ctx, key, r, PutOptions{ContentType, CacheControl})` (заголовки ответа задаёт запись);
- `Head(ctx, key) (Info, error)`;
- `Presigner`: `PresignUpload(key, maxBytes, contentType, ttl)` → метод, адрес, поля/заголовки; `PresignGet(key, ttl,
  responseCacheControl)`;
- `Purger`: `Purge(ctx, publicURLs)`; `NoopPurger` — без CDN и в dev.

**(План media, 26.11, R3.)** В коде: `blob.Buckets{In, Pub, Priv}` (три `Store`) вместо `Bucket(name)`; `Store` —
`Put`/`Get`/`Head`/`Delete`/`List`; `PresignUpload(ctx, UploadSpec{Key, ContentType, Bytes, TTL})` → `UploadForm{URL,
Fields, ExpiresAt, MaxBytes}` — только `POST` (§3.2), файл — последним полем формы `file`; `PresignGet(ctx, key, ttl,
responseCacheControl)` — только бакет `priv`. Открытое хранилище процесса — `blob.Opened{Buckets, Presigner, Purger,
Dev, PublicBaseURL, Available}`. CDN не подключён (R10): `NoopPurger` во всех бинарниках, вызов из `media.purge` есть.

### 6.2. Реализации

- **S3-совместимая** (свой сервер, М15): бакеты `in` (закрытый, жизненный цикл 1 сутки), `pub` (чтение без подписи
  только через домен медиа, §6.5), `priv` (закрытый). Клиент — SDK или совместимая библиотека на чистом Go, последняя
  стабильная; выбор — в плане. **(План media, 26.11, R9.)** `aws-sdk-go-v2/service/s3` + `PresignClient`
  (`PresignPostObject`, `PresignGetObject`), `UsePathStyle=true`, `BaseEndpoint`, `RequestChecksumCalculation` и
  `ResponseChecksumValidation` — `WhenRequired` (иначе S3-совместимые серверы ломают `Put`/`Delete`); подписанные
  ссылки — отдельным клиентом с `BaseEndpoint = *_BLOB_S3_PUBLIC_ENDPOINT` (SigV4 включает хост). Пакет `blob/s3`.
- **FS** (dev, e2e): существующая + бакеты-каталоги + эмуляция подписи (§6.3). Остатки фундамента (коллизии
  meta-путей, имена Windows, `Put` поверх каталога, сегмент > 255, `ENOTDIR` на Linux) закрываются в плане `media`.
- **Memory** (тесты): + `Head`, бакеты, подпись — как у FS.

### 6.3. dev и e2e без облака

При `*_BLOB_BACKEND=fs` api отдаёт вне контракта (**план media, 26.11, R4**: FS повторяет S3 `POST`, клиенты dev и
прода идут одной дорогой; пакет `media/httpdev`):
- ~~`PUT /_blob/in/<ключ>?exp=…&max=…&sig=…`~~ → `POST /_blob/in` — `multipart/form-data` с полями билета (`key`,
  `Content-Type`, `policy`, `x-wf-signature`) и файлом последним полем `file`; подпись — HMAC-SHA256
  `*_BLOB_DEV_SIGN_KEY` над политикой (ключ, тип, точный размер, срок); у пути — своё исключение из лимита тела
  (`httpx.BodyLimit`, §3.6);
- `GET /_media/pub/<ключ>` — публичные варианты; `GET /_media/priv/<ключ>?exp=…&sig=…` — закрытые.
Внешний адрес api, на котором живут эти пути, — `*_BLOB_FS_BASE_URL` (R17, §6.4).
При `s3` и `none` этих путей нет. В прод-образе `fs` не принимается: `backend/Dockerfile` задаёт `WF_BUILD_KIND=prod` (имя `WF_IMAGE` занято
переменной compose с тегом образа), конфиг с `WF_BUILD_KIND=prod` отвергает `fs` (страж — тест конфига и строка в Dockerfile, как `TestProdBuildWithoutE2ETag`;
механизм — решение автора спеки, правится в плане).

### 6.4. Конфигурация и режим `none`

`*_BLOB_BACKEND` — **обязателен, без умолчания**: `fs` | `s3` | `none` (I-1). `none` (стенд Render): `NewUpload`,
`Stage` — `503 media.unavailable` (`media.ErrUnavailable`); `media.Service.Available()` — `false`: владелец
генерируемого (§3.7, `players`) при `false` не рисует и не ставит задач, а `ErrUnavailable` из фоновой задачи — отмена
без повтора, не «мёртвая» (m3-3); очередь `media` пуста; чистка и подписчики работают (объектов нет); CSP без домена
медиа; старт без ключей хранилища. Стенд и свой сервер — один образ, разница только в окружении.

Ключи (префиксы `API_`, `WORKER_`, `ADMIN_`; у встроенного воркера стенда — свои `WORKER_BLOB_*` в `render.yaml`):
`*_BLOB_BACKEND`, `*_BLOB_FS_ROOT`, `*_BLOB_DEV_SIGN_KEY` (только `fs`), `*_BLOB_S3_ENDPOINT` (внутренний адрес),
`*_BLOB_S3_PUBLIC_ENDPOINT` (внешний адрес хранилища для подписанных ссылок — подпись SigV4 включает хост),
`*_BLOB_S3_REGION`, `*_BLOB_S3_BUCKET_{IN,PUB,PRIV}`, `*_BLOB_S3_ACCESS_KEY`, `*_BLOB_S3_SECRET_KEY`,
`*_MEDIA_PUBLIC_BASE_URL`. Новый ключ — сразу в конфиг, `.env.example` и `.env`.
**(План media, 26.11, R17.)** Плюс `*_BLOB_FS_BASE_URL` (только `fs`): внешний адрес api, на котором живут `/_blob` и
`/_media` (dev — `http://127.0.0.1:8080`); у admin-api и воркера — тот же адрес (admin подписывает ссылки на api).
`*_MEDIA_PUBLIC_BASE_URL` при `fs` — пусто или ровно `<FS_BASE_URL>/_media/pub/`.
**(План media, 26.11, Task 4.)** Ключи читает отдельный `config.LoadBlob(prefix, environ)` (как `Mail` у воркера): он же
проверяет набор ключей режима и отвергает `fs` при `WF_BUILD_KIND=prod`; хранилище открывает фабрика
`blobopen.Open` — отдельный пакет, а не `blob.Open`: `blob/s3` импортирует `blob`, обратный импорт дал бы цикл.

Права ключей хранилища выведены из сценариев (I-9; удаление — только задачами воркера):

| Операция | api | worker | admin-api |
| --- | --- | --- | --- |
| подпись загрузки в `in` (`PUT`/`POST`) | да | — | — |
| `HEAD` в `in` («завершить», m1) | да | — | — |
| `Put` в `in` (`Stage`) | — | да (генерируемое) | да |
| `Get`/`Delete`/`List` в `in` | — | да | — |
| `Put`/`Delete`/`List` в `pub`, `priv` (`List` — сверка `reconcile`) | — | да | — |
| подпись `GET` в `priv` | да | — | да |

**(План media, 26.11, R2.)** В Garage права — «ключ × бакет × {read, write, owner}»: `write` включает удаление, `read` —
листинг. Ключи: **api** — `in` {read, write}, `priv` {read}; **admin** — `in` {read, write}, `priv` {read}; **worker** —
`in`, `pub`, `priv` {read, write}; `owner` — ни у кого. Отступление от таблицы выше (принято): api и admin технически
могут удалять и листать во `in` и листать `priv` — процессы доверенные, записи и удаления в `pub`/`priv` у них нет,
клиентам выдаются подписи, а не ключи. Страж — `TestMediaS3KeyRights` (`internal/media`, dev-Garage): каждая операция
таблицы своим ключом проходит, запрещённое R2 (запись и удаление в `pub`/`priv`, любой доступ к `pub` у api и admin) —
403; весь путь на трёх ключах — `TestMediaE2ES3`.

  генерирует оператор (`GK` + 24 hex, секрет 64 hex) в `*.env` процессов, `storage-init` импортирует их (`ImportKey`
  admin API Garage) и приводит права к R2; ключа с правом `owner` нет — жизненный цикл `wf-in` (1 сутки), сайт `wf-pub`
  и CORS `wf-in` `storage-init` ставит через admin API (`GARAGE_ADMIN_TOKEN` — только у `storage` и `storage-init`).
  Порядок — `deploy/server/README.md`, «Хранилище файлов». Dev и CI — `bash scripts/s3.sh up` (тот же образ, права R2).
- **Два внешних адреса** (I-7):
  - **домен медиа** (`*_MEDIA_PUBLIC_BASE_URL`, может стоять за CDN): Caddy пропускает **только `GET`/`HEAD` к бакету
    `pub`**, всё прочее — 404; `nosniff`;
  - **адрес хранилища** (`*_BLOB_S3_PUBLIC_ENDPOINT`, **без CDN**): подписанная загрузка в `in` и подписанное чтение
    `priv`; Caddy проксирует без переписывания пути (подпись включает хост и путь), листинг и админка сервера
    хранилища наружу не открыты.
  Страж файлов: Caddyfile — `/priv`, `/in`, `/` и не-`GET` на домене медиа → отказ.
  **(План media, 26.11, R5.)** Публичное чтение — website-эндпоинт Garage (`[s3_web]`, сайт бакета `wf-pub`): Caddy на
  домене медиа пропускает `GET`/`HEAD` на web-порт Garage с `header_up Host <имя сайта бакета>`; корень, `/wf-in`,
  `/wf-priv` — 404, прочие методы — 405; `X-Content-Type-Options: nosniff` ставит Caddy (Garage его не ставит),
  `Cache-Control` и `Content-Type` — метаданные объекта от воркера. Адрес хранилища: `POST`/`OPTIONS` на `/wf-in` и
  подписанные `GET`/`HEAD` в `/wf-priv/*` — `reverse_proxy` в S3-порт Garage без подмены Host (HTTP-апстрим), прочее —
  404. Стражи — тесты `deploy/server` и job server CI.
- **CDN** — только перед доменом медиа, держит копии публичного; закрытое и входящее через него не идут; сброс —
  `Purger`; без CDN — отдача прямо с сервера.
- **Бэкапы — свои:** том хранилища копируется по расписанию; после восстановления — сверка «строка без файла / файл
  без строки» (команда `worker media reconcile`); база может жить отдельно (Neon) — согласование времени копий —
  порядок в `deploy/server/README.md` (m10).
- **Выкатка:** api, worker и admin-api — вместе (как сейчас); `media.process`/`media.purge` — в `queue.WorkerKinds`,
  у admin-api — заглушки `AddForeign`; старый воркер без вида — задача ждёт, объект виден как `processing`.
- **Стенд Render** — `none` (Ц9) до переезда на свой сервер.

## 12. Тесты и стражи (каждый — подсадкой бага)

- Тип по содержимому: заявлен JPEG, внутри PNG/HTML/полиглот/анимированный WebP — отказ или перекодирование; заявленный
  тип на итог не влияет.
- Метаданные: JPEG с GPS/EXIF/XMP → в вариантах нет APP1/XMP; профиль ICC пользователя (в т. ч. подделанный под P3) не
  попадает в вариант байт в байт: у P3 — эталонный профиль сборки, у прочих — нет профиля.
- Бомба: заголовок 30000×30000 → `too_many_pixels` без выделения памяти под пиксели.
- Размер: тело больше предела → `too_large` (FS-эмуляция и S3-совместимый тестовый сервер); перезаливка по живому
  билету между `HEAD` и `Get` не обходит предел. **(План media, 26.11.)** FS — `TestProcessTooLargeAfterReupload`
  (`media/jobs`), `TestDevUploadForm` (`media/httpdev`); S3 — `TestS3UploadExactSize` (`blob/s3`: N ± 1 байт, чужой
  тип, срок), `TestMediaE2ES3/size` (`internal/media`: ровно предел — `ready`; перезаливка по живому билету телом
  больше — отказ хранилища; обход политики ключом с записью во входящее — `too_large`).
- Права (I-5): билет на владельца A, прикрепление к B → `object_unavailable`; чужой загрузивший → то же.
- Транзакции (I-2): ручка с `Idempotency-Key` и `CreateDirectInTx`/`TakeDownInTx` — 2xx, одна закоммиченная tx; откат
  транзакции владельца не оставляет строк.
- Гонки (I-3, I-4, R2-I1): замок строки в параллельной tx → задача ждёт и доводит объект до `ready`; `TakeDownInTx`
  между записью вариантов и публикацией → в хранилище нет `<id>/`, `Purger` вызван; второй исполнитель на `ready`
  не трогает файлы; задача в `retryable` + перезапуск чисткой → дубля нет; три падения процесса →
  `rejected(processing_failed)`, а три обычные ошибки хранилища — нет; «прикрепление ∥ чистка» — ровно один исход.
  **(План media, 26.11, ревью Task 10, m2.)** Чистка строку `pending_upload` моложе суток оставляет и удаляет только
  входящее (§3.9), поэтому «прикрепление ∥ чистка» всегда кончается прикреплением; при расхождении часов api и воркера
  (у api окно ещё живо, у чистки прошло) прикрепление после удаления входящего доводит объект до
  `rejected(processing_failed)` (входящего нет — обычная ошибка до последней попытки). На одних часах (свой сервер,
  стенд) недостижимо. Страж — `TestAttachVsExpiredCleanup` (`media/intx`: настоящий `media.cleanup` на смещённых часах,
  гонка и порядок «чистка, затем прикрепление»).
- Удаление аккаунта (I-6): обнуление `uploaded_by_user` под ролью `worker` проходит CHECK.
- Lottie (I-8): выражение, внешний `fPath`, аудио-слой, `fr = 0`, `data:image/svg+xml` → `unsafe_animation`;
  `data:image/jpeg` с GPS → в выходе WebP без EXIF; неизвестные поля выброшены.
- Закрытое: ни один путь не даёт публичного адреса закрытого; `PrivateURL` после срока — отказ; Caddyfile домена
  медиа режет `/priv`, `/in`, не-`GET` (I-7).
- Режим `none` (I-1): сборка со встроенным воркером и тестовой целью стартует, «начать» → 503.
- Ключи хранилища (I-9): тест на S3-совместимом сервере с политиками §6.4 — каждый сценарий проходит своим ключом.
  **(План media, 26.11, R13.)** `TestMediaS3KeyRights` и `TestMediaE2ES3` (`internal/media`), `TestS3KeyRights`
  (`blob/s3`) на dev-Garage: `bash scripts/s3.sh up` и `eval "$(bash scripts/s3.sh env)"` (переменные

- dev-пути `/_blob`, `/_media` отсутствуют при `s3`/`none`; `fs` в прод-образе не принимается.
- Набор целей одинаков у трёх бинарников; `media.process`/`media.purge` — в списках видов и заглушках.
