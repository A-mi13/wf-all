## 1. Зачем, цели, границы

### 1.1. Зачем

Картинки нужны полям (найти и оценить поле), каталогу `economy` (аватары, гербы, косметика — монетизация и
достижения), модерации (улики в спорах и жалобах) и поддержке. Спека бэкенда отдала `media` загрузку, проверку типа
по содержимому, перекодирование и отдачу с отдельного домена, а S3-реализацию `platform/blob` — этой спеке. Модуль
стоит в порядке §13 перед `economy`: первым его потребителем будут ассеты каталога, затем фото полей.

### 1.2. Цели

| # | Цель | Критерий |
| --- | --- | --- |
| Ц1 | Один механизм на три режима: публичное от людей, закрытое от людей, ассеты сотрудников | §3; владельцы не пишут своей загрузки |
| Ц2 | Тяжёлые файлы не идут через API | клиент грузит прямо в хранилище (§3.1); API выдаёт билет и принимает «загружено» |
| Ц3 | Наружу — только перекодированное | оригинал не отдаётся никогда; метаданные (EXIF, GPS, XMP, ICC-комментарии) вычищены перекодированием (§3.3) |
| Ц4 | Тип — по содержимому, не по имени и заголовку | сигнатура и успешное декодирование (§3.3) |
| Ц5 | Закрытое не утекает | отдельное хранилище, отдача — короткой подписанной ссылкой после проверки прав владельцем (§3.5) |
| Ц6 | Снятое модератором исчезает | удаление из хранилища и сброс кэша CDN (§3.8) |
| Ц7 | Ничего не копится | брошенные загрузки, отклонённые и откреплённые объекты удаляет чистка (§3.9) |
| Ц8 | dev и e2e без облака | `platform/blob` на файловой системе с эмуляцией подписанных ссылок (§6.3) |

### 1.3. Не-цели (делают другие)

| Что | Кто |
| --- | --- |
| Кто вправе грузить и куда прикреплять (фото поля, ассет, улика) | модуль-владелец: `pitches`, `economy`, `moderation`, `results`, поддержка, `chat` (§2.3) |
| Аватары и гербы как предметы, их выдача (бесплатно, за достижение, за деньги) | `economy` (каталог, инвентарь) |
| Жалобы на фото, очередь и решение модератора | `moderation` (`abuse_reports`), карточка в админке — владелец экрана (§3.8) |
| Колонки-ссылки владельцев: `pitches.photo_urls`, `catalog_items.asset_url`, `ad_placements.image_url` | спеки владельцев переводят их на `media_objects` (спека бэкенда §11) |
| Рисование карточки игрока для шаринга | `players`; `media` только хранит результат (§3.7) |

### 1.4. Анти-цели (не делаем никогда)

- Не отдаём оригинал файла пользователя — только перекодированные варианты.
- Не храним и не показываем фото людей; не делаем загрузку аватара и своего логотипа команды (М1–М3).
- Не принимаем видео (М8).
- Не публикуем закрытое: улики и скриншоты поддержки не получают публичного адреса ни на каком шаге.
- Не доверяем `Content-Type`, расширению и размеру, которые назвал клиент: всё перепроверяет воркер.
- Персональные данные — не в ключах хранилища, не в событиях, не в аргументах задач, не в логах.

## 2. Граница модуля

### 2.1. Что в `media`

- билеты загрузки (`media_uploads`): подписанная ссылка на «входящее», срок, предел размера, цель;
- объекты (`media_objects`): состояние, видимость, владелец по ссылке (тип и id), кто загрузил;
- конвейер обработки (задача `media.process`): проверка, перекодирование, варианты, проверка содержимого (порт);
- отдача: публичные адреса вариантов, короткие подписанные ссылки на закрытые;
- снятие и удаление, сброс кэша CDN (порт), чистка;
- S3-реализация `platform/blob` и эмуляция подписанных ссылок для dev.

### 2.2. Владение и связь с владельцами (решение автора спеки)

Объект создаёт `media`, а «чей он» решает владелец: пока объект не прикреплён, он ничей и будет удалён чисткой (§3.9).
Прикрепление и открепление — в транзакции владельца, вместе с его строкой (фото поля, предмет каталога, улика):

```go
// media/intx
AttachInTx(ctx, tx pgx.Tx, objectID uuid.UUID, owner media.OwnerRef) (media.Object, error)
DetachInTx(ctx, tx pgx.Tx, objectID uuid.UUID, owner media.OwnerRef) error
// OwnerRef{Type: "pitch_photo" | "catalog_asset" | "dispute_evidence" | "report_evidence" | "support_attachment" | "chat_image", ID}
```

- `AttachInTx` берёт строку объекта `FOR UPDATE`: объект не загружен, отклонён, удалён, прикреплён к другому
  владельцу или его цель (§3.1) не совпадает с типом владельца — ошибка (`media.object_unavailable`); повтор с тем же
  владельцем — без изменений (идемпотентно).
- Загрузивший должен совпадать с субъектом, от имени которого владелец прикрепляет (игрок или сотрудник): чужой
  объект по угаданному id не прикрепить.
- `DetachInTx` переводит объект в `detached`; файлы удаляет чистка после срока (§3.9) — откат транзакции владельца
  ничего не теряет.
- Читают владельцы через представление `media_read_objects` (§5.4): состояние, видимость, варианты.

### 2.3. Соседи

| Модуль | Что делает с `media` |

## 3. Сценарии

### 3.1. Загрузка (игрок и сотрудник)

Цель загрузки (`purpose`) — запись реестра, которую объявляет модуль-владелец при сборке бинарника (как действия
подтверждений): имя, видимость (`public` | `private`), допустимые форматы, предел байтов и пикселей, варианты (§3.4),
нужна ли проверка содержимого (§3.3). Права на цель проверяет владелец в своей ручке — `media` их не знает.

1. Клиент вызывает ручку владельца «начать загрузку» (например `POST /v1/pitches/{id}/photos/uploads`): владелец
   проверяет права и вызывает `media.Service.NewUpload(ctx, purpose, uploader, declared)`, где `declared` — тип и
   размер, которые назвал клиент (только для отказа заранее).
2. `media` создаёт объект `pending_upload` и билет: подписанная ссылка на ключ `in/<object_id>` во «входящем»
   хранилище, метод, обязательные заголовки, срок 15 минут, предел размера. Ответ — общая схема `UploadTicket`
   (§7.1). Лимиты — §3.11.
3. Клиент кладёт байты прямо в хранилище по ссылке.
4. Клиент вызывает ручку владельца «завершить» (например `POST /v1/pitches/{id}/photos {upload_id}`): владелец в
   своей транзакции вызывает `media/intx.AttachInTx` и пишет свою строку; `media` в той же транзакции переводит
   объект в `uploaded` и ставит задачу `media.process` (вставка River в той же tx). Если во «входящем» файла нет —
   `409 media.upload_incomplete` (проверка `HEAD` до транзакции).
5. Ответ владельца — его ресурс с `MediaImage` в состоянии `processing` (§7.1). Готовность клиент видит при следующем
   чтении; push о готовности не нужен — обработка секунды.

Сотрудник (ассеты каталога) грузит через admin-api, а не напрямую в хранилище (§3.6).

Веб (`apps/web`) грузит так же, напрямую в хранилище: ручки «начать» и «завершить» идут через BFF, а байты — из
браузера по билету. Нужны CORS «входящего» только для origin продукта и `connect-src` веба с адресом хранилища;
способ билета (§3.2) выбирается с учётом браузера (решение автора спеки).

### 3.2. Предел размера при прямой загрузке

Подписанный `PUT` в S3 не ограничивает размер тела. Поэтому (решение автора спеки):

- где хранилище поддерживает подписанный `POST` с политикой `content-length-range` — билет выдаётся им;
- где нет — подписанный `PUT` с обязательным `Content-Length` в подписи (клиент обязан назвать размер, тело другого
  размера хранилище отвергнет);
- в любом случае воркер проверяет фактический размер (`HEAD`) до чтения и отклоняет превышение; «входящее» живёт
  сутки (правило жизненного цикла хранилища + чистка §3.9).

Какой из способов поддерживает выбранный провайдер — проверить первым шагом плана (§13).

### 3.3. Обработка (задача `media.process`, очередь `media`)

Идемпотентна: повтор после сбоя начинает с начала и перезаписывает те же ключи.

1. Строка объекта `FOR UPDATE SKIP LOCKED`; не `uploaded`/`processing` — задача завершается (уже сделана или снята).
   Состояние → `processing`.
2. `HEAD` входящего: размер ≤ предела цели; иначе `rejected` (`too_large`).
3. Чтение заголовка без полного декодирования: сигнатура (magic bytes) — один из форматов цели, размеры в пикселях ≤
   предела (по умолчанию 40 Мп; защита от «декомпрессионной бомбы»); иначе `rejected` (`unsupported_type` /
   `too_many_pixels`).
4. Полное декодирование с ограничением памяти (размер буфера считается из размеров до декодирования); сбой —
   `rejected` (`corrupt`). Ориентация EXIF применяется к пикселям.
5. Проверка содержимого (порт `ContentCheck`, §8) для целей, где она включена: «недопустимо» — `rejected`
   (`content_rejected`); недоступна — по политике цели (§8.2).
6. Варианты (§3.4) перекодируются заново из пикселей — метаданные не переносятся ни в одном варианте; ключи —
   `pub/<object_id>/<вариант>.<расш>` (публичные) или `priv/<object_id>/<вариант>.<расш>` (закрытые).
7. Строки вариантов, состояние `ready`, событие `media.object_ready` (id, цель, владелец; без адресов) — в одной
   транзакции; затем удаление входящего.
8. Отклонение: состояние `rejected` с кодом причины, событие `media.object_rejected` (владелец снимает ссылку своим
   подписчиком или показывает «не принято»), входящее удаляется.

Форматы на входе: JPEG, PNG, WebP; у анимированных ассетов — Lottie-JSON (§3.6). На выходе растр — только WebP (М12). HEIC/HEIF клиент
переводит в JPEG до загрузки: декодера HEIC без cgo может не оказаться (образ собирается с `CGO_ENABLED=0`); найдётся
рабочий на чистом Go на шаге проверки (§13) — HEIC принимается на входе тоже (решение автора спеки по М12).

Библиотеки — только на чистом Go (без cgo), последние стабильные; выбор — в плане.

### 3.5. Закрытые файлы

- Хранилище закрытого — отдельное (`priv/…`), без публичного доступа; публичного адреса у закрытого объекта нет ни на
  каком шаге (страж §12).
- Показ: ручка владельца проверяет права (модератор города, сторона спора, сотрудник поддержки) и вызывает
  `media.Service.PrivateURL(ctx, objectID, variant)` → подписанный `GET` на 5 минут (решение автора спеки).
  Ссылка не кэшируется клиентом дольше срока.
- Аудит чтения закрытого (кто и что смотрел) — у владельца (`audit.WriteRead`), как контакты заявителя в `identity`.

### 3.6. Ассеты сотрудников (admin-api)

- Грузит сотрудник с правом на цель (`economy.catalog.manage` и т. п. — спека `economy`) **через admin-api**:
  `multipart/form-data`, предел 5 МБ (решение автора спеки). Причины: браузеру админки не нужен CORS к хранилищу и
  `connect-src` за пределами `'self'` (CSP admin-api, `httpapi/admin/static.go`); файлы маленькие.
- Одна операция владельца в admin-api (например «добавить ассет предмета», «заменить фото поля»): приём `multipart` →
  `media.Service.UploadDirect(ctx, purpose, uploader, r, declared)` кладёт байты во «входящее» и создаёт объект
  `pending_upload` → в транзакции владельца `AttachInTx` (объект → `uploaded`, задача `media.process`) — тот же
  конвейер §3.3, в одном запросе, без отдельного «завершить» (решение автора спеки). Загрузивший — сотрудник, он же
  субъект прикрепления (§2.2). Фото поля от модератора («заменить») проходит ту же проверку содержимого, что от игрока.
- Анимированные ассеты (архетип в топе рейтинга, анимация празднования) — **Lottie** (М14), своя цель
  `catalog_animation`. Конвейер: разбор JSON с пределом размера (по умолчанию 1 МБ) и глубины; отказ (`reject_code`
  `unsafe_animation`), если есть ссылка на внешний файл (`assets[].u`/`p` не `data:`), выражения (поля `x` у
  свойств — JavaScript, браузерный плеер админки мог бы их исполнить) или длительность больше 10 с; вшитые растровые
  картинки (`data:`) — не больше 256 КБ каждая; ужатие (без пробелов и полей вне схемы); `application/json`.
  Сервер Lottie не рисует — поэтому **статичная картинка WebP к анимации обязательна** (списки, уведомления, где
  анимация не к месту): это отдельный объект `catalog_asset`, связь «анимация ↔ статичная» держит `economy`
  (решения автора спеки). Плеер в админке — lottie-web из своей сборки (`script-src 'self'`), выражения в нём
  выключены.
- Показ ассетов в админке требует `img-src` с доменом публичных медиа и (для закрытого) хранилища — правка CSP
  admin-api в плане.

### 3.7. Генерируемое системой

`media.Service.PutGenerated(ctx, purpose, owner, r io.Reader, contentType)` — для `share_card` и будущих: объект сразу
прикреплён к владельцу, проходит тот же конвейер (перекодирование — да, проверка содержимого — нет). Рисует картинку
владелец (`players`).

### 3.8. Снятие (жалоба, решение модератора, удаление владельцем)

- Жалоба на фото поля — `moderation` (`abuse_reports`, новая цель — в спеке `moderation`); счётчик жалоб у фото в
  админке и решение «оставить / удалить / заменить» — экран модерации (М10). **Порядок:** `pitches` (§13 п. 6) идёт
  раньше `moderation` (п. 11) — приём жалоб на фото должен появиться не позже фото полей; это решает спека
  `pitches`/`moderation`.
- `media.Service.TakeDown(ctx, objectID, actor)` (вызывает владелец или модерация): состояние `taken_down`, варианты
  удаляются из хранилища сразу, кэш CDN сбрасывается портом `Purger` (§6.2), событие `media.object_taken_down`.
- «Заменить» — снятие старого и загрузка нового модератором как сотрудником (цель та же, прикрепление — владелец).
- Публичные адреса — с `Cache-Control: public, max-age=86400` (не `immutable` на год): если сброс CDN недоступен,
  снятое исчезает не позже суток (решение автора спеки).

### 3.9. Чистка (задачи `maintenance` воркера)

| Что | Срок | Действие |
| --- | --- | --- |
| `pending_upload`, билет истёк | 1 ч после срока | объект и входящее удаляются |
| `uploaded`/`processing` дольше 1 ч | — | задача `media.process` ставится заново (сбой воркера) |
| не прикреплён (`ready` без владельца) | 24 ч | удаляется (у генерируемого владелец есть сразу) |
| `detached`, `rejected`, `taken_down` | 24 ч | файлы и строка удаляются |
| входящее без строки | 24 ч | правило жизненного цикла хранилища (+ сверка чисткой) |

Пачками `SKIP LOCKED`, граница строгая; удаление файлов идемпотентно (`blob.Delete` несуществующего — не ошибка).

### 3.10. Удаление аккаунта

Фото полей остаются (они о поле, а не о человеке); `media` на событие удаления аккаунта (`identity`) обнуляет
«кто загрузил» у его объектов. Закрытые вложения хранит и удаляет по своим срокам владелец (улики — `moderation`).

### 3.11. Лимиты

| Класс | Ключ | Значение (решение автора спеки) |
| --- | --- | --- |
| `media_upload` (билеты) | игрок | 30 в час, 100 в сутки |
| `media_upload` | IP | 60 в час |
| незавершённые билеты | игрок | не больше 5 одновременно (`429 media.too_many_pending`) |
| ассеты сотрудника | сотрудник | общий класс admin-api |

Лимиты — `ratelimit.DefaultRules`/`SubjectKey`, без своей механики.

## 4. Состояния объекта

```
pending_upload → uploaded → processing → ready → detached → (удалён)
                                    ↘ rejected → (удалён)
ready → taken_down → (удалён)
```

`AttachInTx` разрешён из `pending_upload` (переводит в `uploaded`) и из `ready` (генерируемые и повтор). Переходы
проверяет `domain` модуля, база держит CHECK на допустимые пары «состояние — заполненные поля».

## 5. Модель данных

### 5.1. Миграция

`00NN_media.sql` (номер — в плане): типы, таблицы, индексы, права, представление. Колонки владельцев
(`pitches.photo_urls` и др.) не трогаются — их переводят спеки владельцев.

### 5.2. Таблицы

| Таблица | Поля |
| --- | --- |
| `media_objects` | `id` uuid PK (v7), `purpose` text, `visibility` (`public`/`private`), `state` (§4), `owner_type` text NULL, `owner_id` uuid NULL, `uploaded_by_user` uuid NULL, `uploaded_by_staff` uuid NULL (ровно один или ни одного у генерируемого — CHECK), `declared_type` text, `declared_bytes` bigint, `width`/`height` int NULL, `reject_code` text NULL, `version` int, `created_at`, `uploaded_at`, `ready_at`, `attached_at`, `ended_at` (detached/rejected/taken_down) |
| `media_uploads` | `object_id` PK/FK, `method`, `expires_at`, `max_bytes`; секрета подписи нет — ссылка выдаётся один раз и не хранится |
| `media_variants` | `object_id` FK, `name`, `blob_key`, `content_type`, `width`, `height`, `bytes`; PK (`object_id`, `name`) |

Индексы: очередь чистки по (`state`, `ended_at`), незакреплённые по (`created_at`) где `owner_id IS NULL`, владелец
(`owner_type`, `owner_id`).

### 5.3. Права ролей БД

| Роль | Права |
| --- | --- |
| `api` | `INSERT` объектов и билетов, `SELECT`, `UPDATE` состояния и владельца (прикрепление в tx владельца) |
| `worker` | `SELECT`, `UPDATE` состояния и размеров, `INSERT/DELETE` вариантов, `DELETE` объектов (чистка) |
| `admin` | как `api` (ассеты сотрудников, снятие) |

### 5.4. Представление

`media_read_objects` — `id`, `purpose`, `visibility`, `state`, `owner_type`, `owner_id`, варианты (`name`, `blob_key`,
`content_type`, `width`, `height`) агрегатом; без «кто загрузил». Публичный адрес собирает `media.Service`
(`PublicURL(blob_key)` = база публичных медиа + ключ) — владельцы адресов не склеивают.

## 6. Хранилище (`platform/blob`)

### 6.1. Интерфейсы

К существующему `Store` (`Put`, `Get`, `Delete`) добавляются:

- `Head(ctx, key) (Info, error)` — размер и тип без чтения;
- `Presigner`: `PresignUpload(key, maxBytes, contentType, ttl)` → метод, адрес, поля/заголовки; `PresignGet(key, ttl)`;
- `Purger`: `Purge(ctx, publicURLs)` — сброс CDN; реализация «ничего» для dev и для отдачи без CDN.

### 6.2. Реализации

- **S3-совместимая** (прод — своё хранилище в `deploy/server`, М15): три пространства — входящее (`in/`, закрытое, жизненный цикл 1 сутки), публичное
  (`pub/`, чтение всем через домен медиа), закрытое (`priv/`). Три бакета с политиками и ключами
  по бинарникам (§6.4). Клиент S3 — официальный SDK или совместимая библиотека на чистом Go, последняя
  стабильная; выбор — в плане.
- **FS** (dev, e2e): существующая, плюс эмуляция подписанных ссылок — §6.3. Остатки фундамента (memory
  `foundation-3-leftovers`: коллизии meta-путей, имена Windows, `Put` поверх каталога, сегмент > 255, `ENOTDIR` на
  Linux) закрываются в плане `media`.
- **Memory** (тесты): существующая + `Head`, подпись — как у FS.

### 6.3. dev и e2e без облака

При `*_BLOB_BACKEND=fs` api отдаёт вне контракта:
- `PUT /_blob/in/<ключ>?exp=…&sig=…` — приём файла по «подписанной» ссылке (HMAC с локальным ключом, срок, предел
  размера) — клиенту разницы с облаком нет;
- `GET /_media/<ключ>` — публичные варианты; `GET /_media/priv/<ключ>?exp=…&sig=…` — закрытые.
В прод-сборке и при `s3` этих путей нет (страж).

### 6.4. Конфигурация

Новые ключи (по бинарникам с префиксом: `API_`, `WORKER_`, `ADMIN_`) — `*_BLOB_BACKEND` (`fs` | `s3`), `*_BLOB_FS_ROOT`,
`*_BLOB_S3_ENDPOINT`, `*_BLOB_S3_REGION`, `*_BLOB_S3_BUCKET_{IN,PUBLIC,PRIVATE}`, `*_BLOB_S3_ACCESS_KEY`,
`*_BLOB_S3_SECRET_KEY`, `*_MEDIA_PUBLIC_BASE_URL` (домен медиа — конфиг деплоя, как домен продукта в identity В7),
`*_BLOB_DEV_SIGN_KEY` (только `fs`). Ключи доступа — у каждого бинарника свои, с минимальными правами: api — подпись
загрузки во входящее и чтения закрытого; worker — чтение входящего, запись и удаление публичного и закрытого; admin-api
— запись во входящее, подпись чтения закрытого. Новый ключ — сразу в конфиг, `.env.example` и `.env`.

### 6.5. Развёртывание (М15)

- **Свой сервер** (`deploy/server`): сервис S3-совместимого хранилища в compose со своим томом; при первом старте —
  бакеты `in`/`pub`/`priv`, правило жизненного цикла `in` (1 сутки), пользователи с политиками на бинарник
  (§6.4). Наружу открыт только публичный бакет — через Caddy на домене медиа (`*_MEDIA_PUBLIC_BASE_URL`); входящее —
  только подписанной загрузкой, закрытое — только подписанным чтением на 5 минут (тоже через Caddy, свой путь).
  Какой сервер (MinIO, Garage, SeaweedFS или другой) — первый шаг плана с проверкой лицензии и способа поставки образа
  (§13) **(решение автора спеки)**; код от выбора не зависит — протокол S3.
- **Бэкапы — свои:** резервная копия тома хранилища вместе с бэкапом базы и проверка восстановления — порядок в
  `deploy/server/README.md`.
- **CDN:** кэш CDN перед доменом медиа держит только копии публичного (фото полей, ассеты); оригиналы — у нас;
  закрытое через CDN не идёт никогда; сброс по адресу — порт `Purger` (решение автора спеки; без CDN — отдача прямо
  с сервера).
- **Стенд Render** диска не имеет, а облако третьей стороны исключено (М15): стенд работает с пустым реестром целей
  (§12a) до переезда на свой сервер; dev и e2e — FS-эмуляция (§6.3).

## 7. Контракт

### 7.1. Общие схемы (`contracts/openapi/public/media.yaml`, `components`)

- `UploadTicket`: `upload_id` (uuid), `method` (`PUT` | `POST`), `url`, `headers` (объект строк), `fields` (для `POST`),
  `expires_at`, `max_bytes`, `accepted_types`.
- `MediaImage`: `id`, `state` (`processing` | `ready` | `rejected`), `reject_code` (при `rejected`), `variants` — объект
  `{имя: {url, width, height, content_type}}` (у `processing` пуст).
- `PrivateMediaLink`: `url`, `expires_at`.
- `UploadRequest` (тело «начать загрузку» владельца): `content_type`, `bytes`.

Своих операций у `media` в публичном контракте нет: ручки «начать», «завершить», «показать закрытое» — у владельцев,
со ссылками на эти схемы. Админка — то же (`contracts/openapi/admin/media.yaml`, схемы и `multipart`).

### 7.2. Коды ошибок

| Код | Статус | Когда |
| --- | --- | --- |
| `media.unsupported_type` | 422 | заявленный тип не из цели (заранее) |
| `media.too_large` | 422 | заявленный размер больше предела |
| `media.too_many_pending` | 429 | больше 5 незавершённых билетов |
| `media.upload_incomplete` | 409 | «завершить» без файла во входящем |
| `media.upload_expired` | 410 | билет истёк |
| `media.object_unavailable` | 409 | объект не годится для прикрепления (§2.2) |

Причины отклонения при обработке (`reject_code`, открытый enum): `too_large`, `unsupported_type`, `too_many_pixels`,
`corrupt`, `content_rejected`, `unsafe_animation`.

`media` — слой 2 (`archtest/modules.go`). Не импортирует владельцев; реестр целей заполняют владельцы при сборке

## 12. Тесты и стражи (каждый — подсадкой бага)

- Тип по содержимому: файл с расширением и заявленным типом JPEG, а внутри PNG/HTML/полиглот — отклонён или
  перекодирован; заявленный тип не влияет на итог.
- Метаданные: фикстура JPEG с GPS и EXIF → ни в одном варианте нет EXIF/XMP (байтовая проверка маркеров APP1).
- Бомба: заголовок 30000×30000 → `too_many_pixels` без выделения памяти под пиксели.
- Размер: тело больше предела → `too_large` (FS-эмуляция и S3-совместимый тестовый сервер).
- Закрытое: ни один путь не даёт публичного адреса закрытого объекта; `PrivateURL` после срока — отказ.
- Прикрепление: чужой объект (другой загрузивший) — отказ; к двум владельцам — отказ; повтор тем же — без изменений;
  гонка «прикрепление ∥ чистка незакреплённого» — ровно один исход (`FOR UPDATE` против `SKIP LOCKED`).
- Повтор обработки: задача упала после записи вариантов — повтор даёт тот же итог без дублей строк.
- Снятие: после `TakeDown` варианты отсутствуют в хранилище, `Purger` вызван с их адресами.
- dev-пути `/_blob`, `/_media` отсутствуют в сборке при `s3` и в прод-образе.
- Набор целей одинаков у трёх бинарников.

## 12a. Объём плана `media` (решение автора спеки)

Владельцев в коде ещё нет, поэтому план поставляет механизм целиком, а первого настоящего владельца — план `economy`
(ассеты каталога), как капитанство I-4 поставило механизм с портами «недоступно»:
- модуль `media` (сервис, `intx`, конвейер, чистка, представление, события), S3-реализация и FS-эмуляция `blob`,
  общие схемы и коды в контракте (`components`; страж контрактов операций не требует);
- тестовая цель `e2e_image` (публичная и закрытая) — только в сборке с тегом `wf_e2e`, с тестовыми ручками
  «начать / завершить / показать закрытое» в api и admin-api под тем же тегом: на ней — живой e2e и стражи, в том
  числе «набор целей одинаков у трёх бинарников»; в прод-образе целей нет (пустой реестр — модуль ничего не принимает);
- выкатка: `deploy/server` — сервис хранилища, бакеты, ключи, Caddy, бэкап (§6.5); стенд Render — пустой реестр целей.

## 13. Не проверено — проверить первыми шагами плана

1. Сервер своего S3-совместимого хранилища (М15): лицензия и поставка образа, подписанный `POST` с
   `content-length-range` или `PUT` с `Content-Length` в подписи, правила жизненного цикла, политики по
   пользователям, работа за Caddy; сброс кэша CDN по адресу.
2. Библиотеки на чистом Go (без cgo; допускается libwebp/libheif в WASM): **кодирование WebP с потерями и с
   прозрачностью**, декодирование HEIC, ресайз с приемлемым качеством; память и время на 40 Мп. Нет надёжного
   кодировщика WebP — запасной вариант: JPEG для фото и PNG для прозрачного (правка §3.4, контракт не меняется:
   клиент берёт `content_type` из ответа).
3. Клиент Flutter: перевод HEIC → JPEG до загрузки, загрузка по `PUT`/`POST`-билету, пакет Lottie играет наши
   ассеты без выражений и внешних файлов (с нативщиком).
