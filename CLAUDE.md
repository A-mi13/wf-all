# WhereFootball — контекст для Claude Code

Приложение для организации дворового футбола. Капитан собирает команду и матч,
игрок находит игру своего уровня в своём городе.

Отвечай по-русски. Комментарии в коде — по-русски, идентификаторы — по-английски.

## Стек

| Слой | Решение |
| --- | --- |
| Бэкенд | Go 1.25+, `net/http` + chi, модульный монолит |
| БД | PostgreSQL 16+, `pgx` + `sqlc`, миграции через goose |
| Кэш и очереди | Redis/Valkey, фоновые задачи через River |
| Публичный веб | Next.js (SSR, индексируется, OG-превью) |
| Мобильные | Flutter, подключаются к тому же API позже |
| Админка | React + Vite, отдельный домен и отдельный бинарник |

Порядок работ: сначала веб на Next.js, Flutter потом. Приложения в сторы
не идут до трекшна, юрлица пока нет.

## Структура репозитория

```
/cmd/api          HTTP API для приложений и веба
/cmd/admin-api    ОТДЕЛЬНЫЙ бинарник админки
/cmd/worker       фоновые задачи, пуши, ночные пересчёты
/internal/identity   аккаунты, сессии, роли
/internal/geo        страны, города, районы, поля
/internal/teams      команды, составы, заявки
/internal/matches    матчи, слоты, вызовы, протоколы
/internal/stats      агрегаты, рейтинги, таблицы
/internal/reputation надёжность, флаги, санкции
/internal/economy    очки, кредиты, косметика, подписки
/internal/notify     пуши, шаблоны, настройки
/internal/moderation очереди, жалобы, аудит
/internal/platform   БД, логи, конфиг, фича-флаги
/migrations       схема БД (уже написана и проверена)
/openapi          контракт API
```

Модули общаются только через явные интерфейсы верхнего уровня и события.
Никто не лезет в чужие таблицы напрямую — это проверяется линтером в CI.

## База данных

Схема в `/migrations` — 10 миграций, проверены накатом и откатом.
Читай `migrations/README.md` перед тем, как менять схему.

Ключевое, что уже гарантировано базой и что **не надо дублировать в коде**
как единственную защиту:

- два матча на одном поле в пересекающееся время — `EXCLUDE` + зазор 10 минут;
- одинаковые названия команд в городе и клоны латиницей — `normalize_text()`;
- один капитан — одна команда в городе;
- платный матч без суммы и бесплатный с суммой;
- прогнозы только за заработанные очки, не за купленные кредиты;
- больше трёх снятых броней позиции у игрока в команде;
- изменение записи аудит-лога.

Проверки в коде всё равно нужны — но ради понятной ошибки пользователю,
а не ради целостности.

## Правила, которые легко нарушить

**Деньги за аренду платформа не принимает никогда.** `rent_total_minor` — это
справочный расчёт, `payment_notes` — заметки капитана. Не добавляй эквайринг,
эскроу, кошельки и «оплату матча». Выручка только с подписок и внутриигровой
валюты через штатные IAP.

**Суммы — только `int64` в минорных единицах** плюс код валюты ISO 4217.
Никакого `float`. Валюта берётся из страны города, руками не выбирается.

**Время — `timestamptz` в UTC.** Матч «в 20:00» — это время поля, а не телефона
игрока. Таймзона лежит у города.

**Возраст не хранится.** Есть дата рождения и функция `age_years()`. Пороги
живут в `countries.min_signup_age` и `countries.age_of_majority` — это поля,
а не константы: в ЕС порог цифрового согласия плавает от 13 до 16.

**Роли — это `role_assignments` со скоупом,** а не колонка в `users`.

**Все мутирующие запросы принимают `Idempotency-Key`.** Мобильный интернет
теряет ответы, люди жмут кнопку дважды.

**Все строки интерфейса — в файлах локализации с первого коммита,** включая
админку. Русский и английский.

**События пишутся в `outbox` в той же транзакции, что и данные.**

## Чего сейчас НЕ делаем

Чат (комментарии под матчем с лимитом — достаточно), турниры, городские
рейтинги, подписки, кредиты, косметика, прогнозы, второй язык интерфейса.
Инфраструктура под всё это в схеме есть, фича-флаги в сиде выключены.

## Ближайшая задача

Вертикальный срез на вебе: регистрация → создать команду → создать матч →
расшарить ссылку → записаться → закрыть протокол. Без дизайна, на стандартных
компонентах. Критерий готовности — через него можно собрать реальный матч.
